## 0. 现状问题（P0，先修）

### 0.2 一个工具炸掉 = 全部不显示（验收时发现，已修）

`XScatterPointRenderer.SetPoints(positions, colors)` 第一句就读 `positions.Length`，
而散点工具在"没有点"时传了 `null` 表示清空 ⇒ NRE。这个异常发生在 `XChartToolsManager.RenderAll()`
的循环里，**没有隔离**，于是循环中断：排在它后面的所有工具当帧以及之后都不再渲染。
现象就是"我加了一个圆柱元素，所有元素都不显示了"——跟圆柱没关系，是散点先炸了。

修法两半，都要：

1. `null` 表示清空就在渲染器里当清空处理（并在工具侧改用 `ClearAll()`）——**"没有数据"不是一个可以
   被解引用的对象**；
2. 渲染/更新循环按工具隔离：一个工具抛异常 ⇒ 报一次带**工具名**的日志，其余工具继续。
   隔离但不吞：静默跳过会让更多人变成"不知道为什么没画"。

判据：`grep -rn "SetPoints(null)" Runtime` 为空；`RenderAll` 里每个 `OnRender()` 都在 try 里。

### 0.3 只有最内层能折叠（验收时发现，已修）

`MakeBox` 返回的是带边框的容器，而折叠回调切换的是它内部那个空 `inner`；大分类的内容却直接加在了
外框上 ⇒ 点标题只把空容器藏了，内容照旧显示，看上去"大分类不能折叠，只有最小分组能折"。

约定：**一个可折叠块 = `Root`（描边 + 标题）+ `Body`（内容）**，两件事必须分开——
挂进父级时挂 `Root`，放内容时只放 `Body`。谁往 `Root` 上加内容，谁的折叠就无效。

判据：面板里不存在 `Root.Add(内容)`（只有父 `Body.Add(子 Root)`）；`MakeGroup` 一次把 `Root` 与 `Body` 都交出来，
调用点必须显式选一个——选错在面板上立刻能看见（就是这次那样），所以它是个能被一眼证伪的约定。

### 0.1 面板（原 P0）

层级面板在"添加元素"之后：新元素出现在元素板块里，但**其它折叠栏打不开，或打开后没有任何条目**。

根因（机制层面，可核对）：

1. 面板用一个挂在**根节点**上的冒泡监听 `RegisterCallback<ChangeEvent<bool/int/float/...>>` 来发现"值变了"。
   `Foldout` 本身就是 `INotifyValueChanged<bool>`，所以**点一下分组标题也被当成"值变了"**，进而
   `ApplyModifiedProperties()` + （结构签名变化时）`RebuildTree()`。
2. Unity 在带值的元素挂上面板时，会发一次 `isDefaultValue` 的通知（`bool` 的默认值是 `false`）。
   我的回调把它当用户操作写进展开状态字典 ⇒ 每次重建后**所有分组的展开状态被打回 false**。

两条叠在一起的表现就是：一次结构性操作之后，展开即重建、重建即全折叠，看上去"打不开/空的"。

判据（修完之后必须成立、修之前必须能红）：

- 展开状态只由**用户点击**改变，不由挂起时的默认通知改变；
- 点的/数的值改变**不重建**面板树；只有增删/移动/换类型才重建；
- 折叠栏的开关不触发任何 `serializedObject.ApplyModifiedProperties()`（用一个"操作计数"断言：
  纯展开/折叠 100 次 ⇒ 计数为 0）。

## 1. 职责划分：chart 管数据，工具只管呈现

- **chart = 数据的所有者与管理者**。所有"这条轴/这个散点显示哪一段数据"的**数据范围**都属于 chart 的基础数据板块，
  不属于任何工具。工具只问 chart 要"已经算好的东西"，自己不存数据、不解释数据语义。
- **工具（渲染器）= 只呈现**。立方体网格背景、线框、散点、轴线、圆柱、箭头……全部是同一类东西：
  拿 chart 给的空间/数据范围/颜色，把自己画出来。
- 面板因此只有两个板块（顺序固定）：
  1. **基础**：基本变换（四元数姿态、半边长、尺寸口径、中心偏移）、颜色（全局色板）、**数据**（维度、数据范围、
     记录/版本统计）、调试（显示节点、重建、回收）。
  2. **工具**：图里挂的每个渲染工具一个可折叠块，块内只有该工具的呈现参数。

判据：

- **范围类**字段（手动 min/max）不再出现在任何工具上：它们只有一处主人——chart 数据板块里的**维度行**
  （`XChartDimensionDefinition` 的 `OverrideMin` / `OverrideMax` / `ManualRange`，经
  `IXChartRenderContext.TryResolveDomain(dimension, out min, out max)` 生效，
  工具连范围都不用传）。
- **绑定类**字段（"这条轴画哪一维"）留在工具上，2026-10-22 验收时他明确选了这一支：
  它回答的是"呈现哪一路数据"，不是"数据范围多少"；散点用它选颜色映射维、箭头用它选起点维，
  收归 chart 会让"乘几维"这件事从元素上消失。收归的只有范围。
- 面板顶层只有"基础"和"工具"两个板块；工具块里剩下的全是呈现参数（刻度数、次刻度、标签源、
  格式串、颜色、走向…）——没有范围。
- 数据板块里**每个维度一行**：显示名 / 覆盖开关 / 覆盖范围 / 可见，外加一行当前生效范围的说明
  （自动值域＝该维聚合；这一维没数据就直说"轴这一帧不会出现，勾覆盖可先摆出来"）。

## 2. 可控绘制流程（谁先画、谁后画、怎么拿数据）

渲染上下文由 chart 建立并持有，工具**不自己 Find 别人**：

```
chart.EnsureInitialized()
  → BuildToolsRoot()          建 [XChartTools] 根（默认：不显示 + 不保存）
  → RegisterTools()           ★脚本注册（派生类唯一集中注册点）
  → RebuildElements()         配置注册
  → EnsureSpace()             没有空间工具就补一个默认的
  → RebuildToolPools()        §5 的池调度（一次遍历所有脏池）
  → OnChartInitialized()      通用收尾

每帧：
  chart.Update()      → 刷新判定（数据版本号 / 请求）
  chart.LateUpdate()  → context.Begin()
                        → for each tool: tool.OnRender(context)
                        → context.End()   提交本帧申请、回收未用槽位（§5）
```

`IXChartRenderContext`（chart 实现，工具只读）至少开放这些口子：

- `Space` / `ProjectionVersion`：拿投影，`Project(p)`、`Compose(toolTransform)`、`GetFaceFrames()`；
- `GetDomain(dimension)`：该维的**显示范围**（由 chart 的数据板块决定，工具不再自己算 min/max）；
- `RequestTextSlots(owner, count)`：见 §5；
- `Palette`：全局颜色（工具自己的颜色是覆盖项，不是唯一来源）。

判据：

- 工具类里不再出现 `FindTool<...>()`（除 chart 自己在初始化时解析空间）；
- 散点/轴线的显示范围来自 `context.GetDomain()`，脚本侧改 chart 的数据范围 ⇒ 两类元素同时变（探针断言）。

## 3. 作用域纪律：编辑器代码不得渗进运行时

- **运行时命名空间的 `using` 不许落在 `#if UNITY_EDITOR` 里**（2026-10-23 现场）：属性参数必须是编译期常量，
  而 `[AddComponentMenu(XericRegistrationPaths.Table + "…")]`、`[ContextMenu(…)]` 这些**在玩家编译也要算得出来**。
  `using XericUI.Core;` 一旦被守卫住，编辑器那套照样绿、只有玩家编译报 CS0103——他贴的三条就是这个
  （`BubbleLayout/BubbleLayoutGroup.cs`、`XTable/Rendering/Component/XericUIActionTable.cs` 与 `.Api.cs`）。
- 这条**由编译门的一支臂强制**：`run_gate.py` 现在除了"运行时（带 UNITY_EDITOR）"和"编辑器"两臂，
  还编一支**玩家臂**——同一份 rsp、同一批源码，只把 `-define:` 里的 `UNITY_EDITOR` 剥掉。
  它上线第一次跑就复现了那三条（同文件同行），修完转绿；以后这类形状不用靠人想起来。
  **盲区记录**：更窄的守卫（`UNITY_EDITOR_WIN` 里用、`UNITY_EDITOR` 里 using）玩家臂也看不见——
  那需要第三支"只带平台宏"的臂，等真出现这一类再说，先记在这里别当成已覆盖。

采用仓库里已有的 **partial 分文件** 约定（参考 `XericUIActionTable.cs` / `.Api.cs` / `.Border.cs`）：

| 文件 | 内容 | 程序集 |
|---|---|---|
| `XChartRenderToolBase.cs` | 呈现、池槽位访问、脏标记：**纯运行时**，不含 `UnityEditor` | Runtime |
| `XChartRenderToolBase.Editor.cs` | `partial`，编辑器侧调试/检视用的数据导出（只读快照，不画图） | Runtime，整体 `#if UNITY_EDITOR` 包裹 |
| `ChartToolXxx.cs` | 具体工具 | Runtime |
| `XChartPanelEditor.cs` / 池的调试绘制 | 面板与手柄 | **Editor** 程序集，运行时绝不引用 |

规则：

1. Runtime 程序集里**不出现** `using UnityEditor`；需要编辑器行为时只有两种写法：`#if UNITY_EDITOR` 整块包裹，或把
   代码放到 Editor 程序集的 `partial` 分文件里。
2. 面板只读运行时暴露的元数据（`[XChartElement]`、字段名、`[Header]`/`[Tooltip]`），不要求运行时提供绘制 API。
3. 调试功能（显示全部节点、强制重建）在运行时暴露**动词**（`RebuildAll()` / `SetGeneratedVisible(bool)`），
   编辑器只负责放按钮。

判据：`grep -rn "using UnityEditor" Runtime/XChart` 为空（除 `#if UNITY_EDITOR` 块内）。

## 4. 面板呈现规范（box 风格 + 标题纪律）

- 分组一律用**带边框和留白的 box** 包裹：标题行（可折叠）+ 内容缩进。板块（基础/工具）是大 box，工具是嵌套 box。
- box 的**左内边距至少 16px**：折叠小三角是 `Foldout` 自带的 toggle，默认样式带负缩进，
  留白不够它就压在左描边上（现象：验收时反馈"box 还是和折叠按钮有冲突，左侧要再往左避让一些"）。
  嵌套层的左缩进只给 4px——左右两侧各自收紧，否则内层标题会被推出可读宽度。
- **标题一经确定不再改**：标题就是字段的短名，语义写在 `[Tooltip]` 里，浮上去看。
  禁止 `标题（一些更新说明）` 这种写法——那是把 changelog 写进 UI。
  ⇒ 现有需要清理的：`空间（四元数姿态 + 半边长）`、`宿主（立方体的哪个面、往哪个方向走）`、
  `填充面（a=前 b=后 …）`、元素行标题 `MeshBg（Cube Mesh Bg Config）` 等，一律改成短标题，说明搬进 Tooltip。
- 元素行的标题只放 `ElementName`；类型名不放标题（放 tooltip 或次级信息行）。
- 判据：面板上所有 `Header` 字符串不含括号；同名字段在两次编译之间标题不变（把标题清单固化进探针/门的一个断言）。
- 折叠的**默认态与开合纪律**（默认全折叠、最深一层互斥）另见 §13——那一节改的就是这一条。

## 5. 文本（及同类组件）对象池

**动机**：编辑器阶段组件的任何变换都不会保存 ⇒ 池在域重载后可能整体不存在 ⇒ 没有语言级保证，
只有"每次用之前校验"这一条路。所以：

### 5.1 申请单位是"一批"，不是"一个"

- 工具**不能** `var t = pool.Get()` 立刻拿组件。必须先算本帧需要几个：`RequestTextSlots(owner, count)`。
- chart 收到的是"某工具的槽位需求脏了"，不是即时分配。
- 派生类通过基类的属性访问已发落的列表：`protected IReadOnlyList<TMP_Text> Texts { get; }`（长度就是申请数），
  越界访问要判空并跳过，**不 NRE、不静默画错**。

### 5.2 一次调度：先释放、再补充、顺位优先、池兜底

```
chart.RebuildToolPools()          // 帧首或脏标记后调用
  1) 收集所有 dirty 的 owner，按申请数排序（先大后小：让先申请者顺位拿到回收件）
  2) 对每个 owner：delta = Requested - Current
     delta < 0 → 归还 |delta| 个到"本帧回收队列"（先处理释放）
  3) 再遍历一次：delta > 0 → 先从"本帧回收队列"取（顺位复用）
     队列空 → 从池 get（池里也没有就新建，标记 DontSave/HideInHierarchy）
  4) 回收队列仍有剩余 → 才真正 release：setActive(false) 放回池
  5) 每个 owner 的列表被换回（换实例而不是原地改长度），并清 dirty
```

要点（就是你的原话的形式化）：申请与释放都走"换列表"，具体实现层不自己维护实例列表；
组件数变化必须重新申请（换回旧列表 → chart 校验有效性/可见性 → 少了补、多了抽）；
抽出来的先给别的 owner 顺位，顺位空了才 get，顺位盈余了才 release。

### 5.3 有效性校验（每次调度都做）

槽位满足下列全部才算可用，否则丢弃并补：`!= null`、`gameObject != null`、`activeSelf` 符合预期、
`transform.parent == 池根`、`(hideFlags & DontSave) != 0`。编辑器域重载后池根可能整个没了——那时
重建池根，而不是抛。

判据（探针可跑，纯 C# 不依赖 Unity 对象也行：把"池"抽象成一个可注入的 `ISlotFactory`）：

- 需求 3→5 再 5→2，两轮调度后：顺位复用次数 = 抽取件被别的 owner 用掉的次数，release 次数 = 队列剩余；
- 两个 owner 争抢有限回收件时，先申请者拿到（排序规则生效）；
- 任何 `Texts[i]` 都不重复发给两个 owner（同一实例不双主）；
- 池根丢失后一次调度能自愈（无异常、数量补齐）。

### 5.4 消费方的三条纪律（写这条是因为雷达那类写法会和校验打架）

1. **不得对发落到的槽位 `SetActive(false)`**：`activeSelf` 是 §5.3 的判据之一，工具自己停用就会
   被下一轮调度当无效丢弃、再补新件——每帧丢弃+新建，计数器一直涨。要隐藏内容就**擦文本**
   （`text = string.Empty`）或者**少申请几个**。
2. **申请数是总数不是增量**，而且必须在 `OnUpdate` 里申请、在 `OnRender` 里落笔：
   chart 的顺序是 `Update → DispatchTextPools → RenderAll`，反了就会出现"这帧申请、下帧才有件"。
3. **只读 `Texts`，不缓存**：池换回列表时旧引用就作废了；取值一律 `i < Texts.Count` 并跳过 null。

**自建文本的残留点（普查口径：`Runtime/XChart` 里 `AddComponent<TextMeshProUGUI>`）**：
只剩 `Pools/XChartTextSlotFactory.cs` 这一处实现。`Axis/ChartToolAxis.cs` 与 `Radar/ChartToolRadarBg.cs`
都已在 P2 迁入池（雷达原先靠逐标签 `SetActive(false)` 隐藏、且数量一变就整数组销毁重建，
按纪律 1 改成"要几个申请几个"：关掉标签就是申请 0 个，件直接回池）。
判据：这条 grep 的命中数必须是 1，且命中文件在 `Pools/` 下——多于 1 就说明又有工具自己造标签了。

**离线测不到的一条**（不是"没测到"，是没有生产者）：`XChartTextSlotFactory.IsAlive` 里
`(hideFlags & HideFlags.DontSave) != 0` 这枚掩码。它要求运行时真有一个 `TMP_Text` 实例，而离线造不出
（在探针里重写一遍同样的表达式＝抄自己的实现，一起错也不会红）。它错起来的形状是"每帧都把发落到的
标签当无效丢弃再补新的"⇒ 画面表现为标签闪烁/干脆不见。
**已有现场证人**：§6 的自述报表在编辑器里拍到 684 次调度、`dropped=0`、`idle` 从未为假，
且每次 `hasRange=True` 都 `want==have`——掩码与父子口径在真环境里被反复验过且没判错过。
枚举数值是现测的（引擎自带 mono）：`DontSave=52`，编辑器旗标 `DontSaveInEditor|HideInHierarchy=5`，
`5 & 52 = 4 ≠ 0`；运行期 `HideAndDontSave=61`，`61 & 52 = 52 ≠ 0`。

## 6. 生命周期、回收与调试

- **chart 下所有生成节点默认：不显示在 Hierarchy + 不保存**。编辑器期 `HideFlags.DontSaveInEditor | HideInHierarchy`，
  运行期 `HideAndDontSave`（`CurrentFlags` 统一给）。
- `chart.RebuildAll()`：销毁 chart 生成的**全部**节点（含池根与池内件）→ 校验目录干净（子节点数 == 0）→
  走 chart 初始化流程 → 每个工具自己的初始化流程。**重建是"chart + 它的全部工具"一起的**，不把重建丢给某个工具。
- 池也提供 `DestroyAllSlots()`（硬销毁），供 `RebuildAll()` 与调试菜单调用。
  **P3 落地形态**：`IXChartSlotFactory.DestroyAll()` + `XChartSlotPool.Dispose()`（调度器只交回列表，
  销毁交给认识"件"的实现），`Teardown()` 里先 `DestroyTextPool()` 再拆工具，
  并且**现拆现验**——池根挂在 chart 自己下面，`[XChartTools]` 的清理带不走它，
  不显式拆就等于每回收重建一次在场景里漏一个 `GeneratedTextPool`（报表会打 `POOL-ROOTS-LEAKED: N`）。
  **这条判据上线第一次跑就抓到了真漏**：验收现场 66 次 `POOL-ROOTS-LEAKED`——
  漏的不是 `RebuildAll()`（它走 `Teardown`，会把池根拆掉），而是**域重载**：复用旧 `[XChartTools]` 时
  只清了 `[XChartTools]` 的子节点，上个域留在 chart 自己下面的池根没人管，新池再建一个就攒一个
  （他重启一次 Unity 正好放大）。修法：`BuildToolsRoot()` 里先 `PurgeLeftoverPoolRoots()`。
  修完同一条判据在同一套按钮流程下 **66 → 0**。
- 调试动词：`SetGeneratedVisible(bool)`（只改显示，**不改保存位**）。
- **自述报表**（编辑器期，整份文件在 `#if UNITY_EDITOR` 里）：工程根存在 `xchart.dump.on` 时，
  每 0.4 秒把这张图的关键内部状态追加进 `xchart.dump.txt`——Canvas 在不在、空间版本号与投影尺度、
  元素表逐行、池的 owners/acquire/reuse/release/dropped/idle、每个工具的可见性与兄弟序号、

## 9. 数据窗口（浏览 / 导入导出 / 复制粘贴）

入口：`Tools/XChart/数据窗口`，或面板"基础 → 数据 → 打开数据窗口"（带着当前图表进去）。

- **虚拟化落在 UI 层**：数据本身仍是 `XChartDataModel` 里那张内存记录表（没有分页、没有懒加载）；
  虚拟化指"只有滚进可见范围的行才被绑定"。窗口顶部自报 `总行数 / 维度 / 已绑定次数 / 最近绑定行`——
  灌一万条后这个次数应停在几十。**把这件事写进窗口里**，免得有人以为数据被分页了。
- **格式只有一份**：导出、导入、复制、粘贴全走 `XChartDataText`（规范 §3）。
  行文本而不是 JSON：运行时程序集没有可依赖的 JSON 库，手写解析器等于自己造一个容易错的轮子；
  行文本还能直接丢进表格软件、在编辑器里逐行 diff、粘贴替换不需要转义嵌套。
- **数值按往返精度写**（`"R"` + 不变文化）：写成 `0.00` 这类格式会在导出→导入之间静默丢精度，
  而那种丢失在图上只表现为"点挪了一点点"，是最难查的一族——探针有一条断言专门钉这个
  （`data text: round trip keeps values bit exact (round-trip precision, not 0.00)`），
  并配一支把格式改成 `0.00` 的变异臂证明它会红。
- **导入是全有或全无**：任何一行不合法就整份拒绝并**指出行号**，绝不半途替换掉一半数据
  （半份数据比没数据更坏）。注意 `double.TryParse("NaN")` 是**成功**的，所以拒绝必须来自
  "值是不是有限"这一步，而不是"能不能解析"——这条也是他现场踩出来的（我第一版期望写错了行号）。
- **破坏性动作**（替换、清空）：先弹确认，且**先把当前数据复制到剪贴板**，误操作能捞回来。

## 8. 验收时发现、本轮未修的（2026-10-22 记）

1. **数据为空时"什么都不画"是设计，但对使用者不友好**：轴线的自动值域来自该维的聚合 min/max，
   图里没写数据时聚合是空的 ⇒ `TryResolve` 两条来源都给不出 ⇒ 轴线整条不出现。
   **P4 已修**：数据板块每个维度一行，行内第一句就是当前生效范围——
   "自动值域 = 该维聚合 a..b"／"覆盖 a..b（自动值域被忽略）"／
   "这一维还没有任何数据 ⇒ 画它的轴这一帧不会出现；勾上覆盖范围并填两个不同的值就能先摆出来"。
   范围本身也搬到这一行（`OverrideRange` + `ManualRange`），工具不再各存一份。
   **（2026-10-25 更新，§21）**：一个总开关表达不出"只钉最小、最大跟着数据跑"，这一行改成
   `OverrideMin` / `OverrideMax` 两端各自可钉；而**行本身**从面板搬进了数据窗口的「维度范围」页
   ——面板的「数据」框整块删除（他："我们将所有的信息都整合到这个窗口里面去"）。
   **这一句写错过一次**（P4 验收现场它印的是"自动值域 = 该维聚合 NaN..NaN"）：面板自己写了一遍
   "聚合存在就算有数据"的判定，而空模型下 `Has(Minimum)` 是**真**、值是 NaN。同一条规则不能有两个实现——
   现在"能不能用"一律问 `XChartDomainMath.TryResolve`，面板只负责把结果说成人话；
   报表那份 `rangeSource` 同理，改成取本帧的结果（`m_HasRange`）而不是再问一遍聚合。
2. **轴刻度与立方体网格的分格没对齐**：刻度由 nice-step 在数据域里铺，网格分格由 `GridDivisions`
   在几何域里铺，两套口径。
3. **立方体网格自身的值域不可调**：背景网格只有分格数，没有"它在数据域里覆盖到哪"的入口。

   **第 2、3 条在 P4 的处理（二选一已定）**：**不派生，改成"可见化 + 手动对齐"**。理由：
   立方体的网格线画在**几何面**上，它跟数据维度没有天然的一一对应——要让分格从刻度派生，
   背景元素就得知道"这个面的 s/t 各对应哪一维"，那是把数据绑定塞进背景元素，
   与 §1 的归属划分正相反（背景只该知道几何）。
   所以：范围一侧已经归到维度行（第 3 条的"值域可调"由此满足——立方体覆盖的就是各维范围，
   散点按同一份范围归一化，所以网格与点天然同一尺度）；分格那一侧只做"算式可见"：
   轴元素行下印一句"主刻度 K 条 = K−1 段 ⇒ 把立方体网格的分格数设成 K−1 就逐线对上"，
   两个旋钮还是各自的旋钮，但对得对不对一眼能算。

   **他随后指出"刻度并没有和网格线对齐，两头都没对齐"——查下去是这个原因**：
   轴的默认跨度是 `0.08 .. 0.95`（内缩的装饰值），而网格线铺的是整面 `0 .. 1`，
   于是两头的刻度必然差着 8% / 5% 的面宽，**改分格数也补不回来**。
   P4 已做三件事：① 默认跨度改成 `0 .. 1`（铺满整面）；② 已存在的元素仍带着旧序列化值，
   所以轴元素行会印"这条轴只铺了 8% .. 95% 的面宽，两头都对不上格线"并给一个**铺满整面**按钮
   （一次点击写 0/1，不静默改数据）；③ 把前提写在提示句里：对齐要求"铺满整面 **且** 范围能被步长整除"。
   **诚实的边界**：聚合出来的范围常常不是"好看"的数（现场就是 `-49.936..49.936`），
   这种范围按 nice-step 铺出来的刻度**落不到格线上**——探针把这条也正面钉住了
   （`grid alignment: a ragged range … cannot land on grid lines`），
   要那种情况也逐线对齐，就得走另一支（网格分格从刻度派生），也就是上面说的"往背景里塞数据绑定"。

   **分格数按方向分（P4 尾巴，他选的"现在就把这条做完"）**：立方体背景的 `GridDivisions`
   变成"统一值 + S/T 各一份"（0＝跟随统一值），算式抽成 `XChartGridDivisions`（纯托管，探针钉住
   "沿 S 的格线由 T 的分格数决定"这一句最容易写反的话）。轴元素行按它自己的走向给出"把哪个方向设成 K−1"，
   并把当前值印出来（`现在 S=0 T=0`）——不然让人满面板找旋钮。**同族里还有一处没跟上**：
   `ChartToolMeshBg`（网格预览产品那份背景）仍是一份分格数，而且它连边线的画法都不一样，
   等它那期一起改；这里如实点名，不假装扫干净了。

   **"轴末端差一点点"这条的判定过程（留着给下次省事）**：先给出可分辨的读数——轴工具自己持有的
   `span=start..end` 印进报表。现场读数：改起点比例时 `span` 从 `0..1` 走到 `0.5..1` 并稳定
   ⇒ **值确实到了工具身上**，"值没传下来"这一支被排除。
   **映射这一支也被排除**（这是可离线证的，不是猜）：线框棱、格线、轴三者共用同一份投影
   （线框走 `Space.Project(Vertices[..])`、格线与轴走面帧 `Map`），而"每个面的四角恰落在立方体顶点上"
   **早就是探针里的一条断言**（见 `XChartCubeGeometry` 面顶点索引表的注释）——
   面帧的 s=0/1 就是该面的两条棱，轴铺满整面时两端必然落在棱上。
   换面后仍然"两端都差"这一现象与之一致：他比的是**立方体轮廓**，而轴画在某个面的**对角线**上，
   那条对角线的两个端点本来就在轮廓内部（CrossRatio=0 时轴还正好压在面的棱上，容易被相邻面的填充盖住）。
   ⇒ 归为**观感层待重构项**（他 2026-10-23 的话："你现在做的框架其实和我想的也有点出入，
   如果这个问题的原因主要出在映射上的话，我们后面再重构吧，你先做完这几个目标"）。
   下次要真判它，得拿像素级证人（把轴的两端、该面四角、以及轮廓六角的像素坐标一起印出来比），
   现在是"他说看着短、机器证明两端正好在棱上"，**两半并存，不合并结论**。
4. **面板：增删元素之后，Inspector 里的元素行会整批消失**（验收时确认的现象，与渲染无关）。
   **数据侧已排除**：684 次采样里 `elements: count` 从没读过 0（最小 2，常见 3），
   而且工具清单与元素表逐项对得上（"表里有但工具没建"的采样数 = 0）——
   所以"行没了"是**面板读数**的问题，不是序列化丢了。
   **P3 已按这一条修**：`m_ElementsProp` 字段删掉，改成 `ElementsProp()` 每次现取
   （`serializedObject.Update()` 之后旧句柄会作废，而作废的 `SerializedProperty` 不报错，
   只安静地报 `arraySize == 0`）。同时面板把自己的读数印进同一份报表：
   `panel: rows=N table=M`，两边不等就打 `ROWS-DISAGREE`。
   **未证的一半**：这条证人的"能红"要在真编辑器里演一次（把 `ElementsProp()` 临时改成返回 null，
   应当看到 `rows=0 table=3 ROWS-DISAGREE`）；离线演不了，所以这里记作**待现场取证**，不算已证。
5. **元素重名会串台**（同一批采样拍到 8 次 `Axis,Axis`）：默认名按类型给，同类加第二个就撞，

6. **点"重新生成全部节点"会抛 `MissingReferenceException: m_AtlasTextures of FontAsset`**
   （P3 验收第二轮的现场）。栈是 UI Toolkit 的按钮文本测量 → `TextCore.Text.FontAsset.TryAddCharacterInternal`。
   **盘上证据**：默认字体资产是 `Assets/Font/OPPO Sans 4.0 SDF.asset`（`TMP Settings.m_defaultFontAsset` 指向它），
   它的 `m_AtlasTextures` 列了 8 项、第 8 项是 `{fileID: 0}`，而 `m_AtlasTextureIndex: 6`：
   盘上那 7 张都在，**第 8 槽是运行时补进去的动态图集**，域重载之后就是一个失效引用。
   所以这不是"重建把资产拆了"，而是**任何一次需要新增字形的文本测量**都会撞上它
   （面板里的中文标签正好在做这件事，点重建只是让文本重新量一遍）。

   **我新加的中文标签**正相关（P3–P7 加了不少新字），而不是与"重建/域重载"正相关。
   判据上的意义：**这条会挡住一切"看一眼面板/图"的验收**（Inspector 每次重绘都可能抛），

   - **面板确实不是 uGUI**：Inspector 走 `CreateInspectorGUI`（VisualElement 树），数据窗口是

     ⇒ 面板每多一句新中文，就要**现场新建一页**，而"新建页"（`TryAddGlyphsToNewAtlasTexture → SetupNewAtlasTexture`）
     正是域重载后旧页 `Texture2D` 引用失效的那一步。**所以"重载 TMP 文本"不会有任何效果**——
     要动的是这份字体资产的**供给方式**，不是文本资产。
   - **另一条同源的放大器**：`TMP Settings.m_fallbackFontAssets` 是**空的** ⇒ 所有中文都往这一份 90pt 的资产里现烤，
     没有任何回退字体分担。

     **一次烘全**，并把 **Sampling Point Size 降到 32–40**（90pt 时 3500 字要 30+ 页；40pt 约 6–7 页），
     之后运行时不再需要新页；② 或给 TMP/TextCore 配一份**含汉字的 fallback**，让默认资产只负责拉丁字形。
   - **离线证不了的一半（如实点名）**：编辑器 UIE 文本**具体取哪一份字体资产**（`TMP Settings` 的默认资产？
     TextCore 自己的 settings？还是 `EditorTextElement` 的内建默认？）我没能在离线射程内定死——
     `EditorTextElement` 这个类型在 `UnityEditor.dll` 与 `UnityEditor.UIElementsModule.dll` 里都**没反射到**，
     `StyleProperties` 也没取到（探针：`.ximage-gate/font_path_probe.cs` / `font_path_probe2.cs`）。
     ⇒ 因此"我代码侧显式给面板指定字体"这条**尚未证成**，不能当成现成的解法承诺。

   **2026-10-24 第二次更正（把上面那条"证不了"收掉一半）**：按名字在**全部**编辑器程序集里扫类型之后：
   - **2022.1 里没有 `EditorTextElement` 这个类型**（上面那句"没反射到"的原因不是路径猜错，是它不存在）。
     编辑器 UIE 用的就是普通 `UnityEngine.UIElements.TextElement`（成员里带 `uitkTextHandle`），
     经 `UITKTextHandle` 桥到 TextCore。

## 10. 圆柱：视角下的外轮廓包边（P6，2026-10-23 按他口述重做）

**他指出的错**（原话）："几何扫描图形的含义是在我们视角下这个图形会呈现出一种外轮廓包边的效果。
所以现在你现在的做法就是直接将圆柱端面的几个顶点都连起来的做法是不对的，应该只显示外边轮廓。
而轮廓的识别就是：将一个圆变形后投影到界面上实际上就相当于将圆压扁成椭圆了，所以椭圆就有长边和短边，
所以过圆心一点的长轴用来连接外边框。"

- **旧实现错在哪**：把相邻端面点按角度连成一片片四边形（侧面）＋ 盖面三角扇。那画出来的
  是"**所有母线都可见**的透视线框"，不是包边——它把背面的轮廓线也画了出来。
- **新实现**：外轮廓 ＝ 两片端面椭圆**采样点集的凸包**（`ConvexHull`，Andrew monotone chain，纯数学）。
  对凸截面这是**精确解**，而且平行/斜置/两端不同法线/两端不同心**都是同一套代码**：
  不必为"斜圆柱"另写切线公式，那两条"过圆心的长轴方向"的桥接线就是凸包自动给出的那两段。
  轮廓只画包边；"把两端顶点全连起来"降级成可选元素（`GeneratrixCount`，**默认 0**）。
- **投影从 2D 算起**（他要求"从两个端面的投影换算开始就应该在 2D 上算，最大限度复用结果"）：
  每片端面只投 **3 次**——圆心 + 盘内两根基（`TryOrthogonalBasis` 取正交基，`TryProjectDisc` 把
  基向量的像素像当半轴）。正交投影是**仿射**的 ⇒ `p(θ) = 中心 + U·cosθ + V·sinθ` 正好是椭圆，
  此后所有采样（轮廓、十字、母线）都在 2D 上按参数式展开，不再对每个点做 3D 投影。
- **可选项各有开关**：`ShowOutline`（包边）、`ShowFill`（填充＝**同一个**凸包多边形，
  中心扇形提交给 `XChartMeshFillRenderer`）、`ShowCapCross`（端面十字）、`GeneratrixCount`（内部母线）。
  十字用 `CrossPoints` 取的是 +U/+V/−U/−V 这四个**采样顶点**（`right − left = 2U`、`top − bottom = 2V`），
  所以它**永远与实际端面对得上**、能看出滚转；若改用椭圆的长短轴，长短轴会随观察方向自己转、把滚转吃掉。
- **两端各自可设法线**（`StartNormal`/`EndNormal`，零向量＝沿两端连线，与旧行为一致）。

**我第一版怎么把"矩形"这条判错的（值得留档，因为教训不是"期望写错了"）**：

- 需求里写的是"两片同形同向、正面朝观察者 ⇒ 凸包为矩形（四点，两两平行）"。我照着这个**姿态**去写断言
  ——用两片"盘面平行于屏幕"的圆盘（`U=(10,0)、V=(0,10)`，圆心相距 40）——结果量出来是 **50 点**，不是 4 点。
  我一度把它记成"我的期望写错了"，并把它改成"真子集 ＋ 四个极值角在包上"。
- 复盘才明白：**错的是我选的姿态，不是那句话**。盘面平行于屏幕时，圆盘投影成整圆，轮廓是**胶囊**：
  两段半圆弧本身就在包上（弧上采样点都是凸点），所以点数 = 两段弧 + 两个接点。
  而"4 点矩形"要的是**端面看到侧刃**——端面平面包含视线方向时椭圆压成一条线段，
  两片平行线段的并集才是**正好 4 个角**的矩形（这才是圆柱从侧面看过去真正的样子）。
- 所以现在两种姿态**都留着**：正面（胶囊，判"真子集 + 四个极值角 + 面积 ≥ 两片之和"）与
  侧刃（**正好 4 点矩形**，判"count == 4 且对边两两平行等长"）。前者还顺手把"点数不是 4"这件事钉住了，
  免得下一个人又把"矩形"当普遍规律。
- 顺手的收获：**侧刃这条是"单调链必须剔掉共线点"唯一的可判定形式**。侧刃姿态下所有采样点**精确共线**
  （`V` 恰为零 ⇒ 每点 y 精确等于圆心 y），把 pop 条件从 `<= 0` 放松成 `< 0` 就会把它们全留下——臂 M 因此有靶子。
- "**面积 ≥ 单片端面**"这条断言**不可能有能红的对照**：凸包含住某一组点 ⇒ 面积不小于那组点，
  于是只要"包住两片"为真，它就永远不能红。**没有能红对照的断言不算门** ⇒ 挪到"两片相距 40"那一对上
  判"面积 ≥ 两片之和"（那里才是独立信息），并配一支"只保留下凸链"的变异臂证明它会红。
  同一条也删掉了一句只判上界的"仍是多边形"——它的内容已被 `count < 2×采样数` 严格覆盖。

**臂 M 顺手抓出一个真实的容量越界（已修）**：`ConvexHull` 的两条链各自最多 push 一次每个输入点，
写入下标最大到 `2×count−3` ⇒ 包点缓冲要能装下 **2×count**；而原来的契约只要求"装下 count"
（`BuildOutline` 里写的是 `segmentCount * 2`，那正好是**采样数**，不是采样数的两倍）。
平时的输入（胶囊 50 点）离边界很远，所以一直没炸；臂 M 把全部 96 个采样点都留在链里，
当场以 `IndexOutOfRange` 打穿了那道门。现在：`ConvexHull` 自己带容量断言、契约改成"output ≥ 2×count"，
工具与探针的缓冲都按这个口径给。**这一条是变异臂第二次抓到"我自己的判据/契约有洞"**。

**判据（离线，全绿）**：门三臂（runtime / player / editor，player 臂剥掉 `-define:UNITY_EDITOR`）
＋ 探针 **268** 项 ＋ `pool_family` ＋ `p2_control` 四臂 ＋ `p4_control` **14 支臂**。
圆柱这 7 条断言各有对照：真子集/侧刃矩形/四点/桥接极值/包住两片/两片面积 ← 臂 I（只保留下凸链）、
J（只采一片端面）、L（**不取凸包、把采样点全交回去 ＝ 他否掉的那种画法**）、M（保留共线点）；
十字 ← 臂 K（改成按屏幕轴对齐）。

**现场读数**：每帧报表里该工具一行带 `outlinePoints= / fill= / cross= / generatrices= / normals=`，
0 也要能分清"没算"（`built=false`，法线退化）还是"算出来是空"——按 §8 的老规矩，零必须说出它零在哪一层。

**本轮明确不做（别当成已覆盖）**：**端面平面去切立方体网格**。他提到两个端面法线"用于在立方体网格中
设定他们的切面"，但本轮他选的是"先只要法线定朝向"，所以**只做了朝向，没做切面交线**。
要让端面真在立方体网格里切出交线，是另一件：需要"平面 × 立方体面"的求交与多边形裁剪，
而且它属于**几何**不属于数据（§1 的归属划分），落点应在空间/背景那一侧，不要塞进数据模型。

### 10.1 第二轮验收（2026-10-23 现场）：默认法线让两端互为镜像 + 端面圆要能闭合

他现场看出两件事，都对着这一期的实现：

- **"两个端面是旋转了吗，它的连接顺序错了"** —— 这是**真的**，根因在默认法线的取法。原来我让两端各自
  "朝另一端"取法线，于是第二片拿到的是**反号**的法线；而 `TryOrthogonalBasis(-n)` 会给出 `u' = -u`
  （叉积对第一个参数反号）⇒ 两片的采样角是**镜像**的：同一个采样下标 i 在两片上指向不同方向，
  可选元素里"两端对应点相连"的母线就拧成 X 形，端面十字两端也互为镜像。
  现在把这条规则抽成纯函数 `XChartCylinderGeometry.ResolveNormals`：**显式法线优先；默认两端都用同一条轴、同向**
  ⇒ 两片参数化完全一致，下标 i 就是同一个 3D 方向。配了一支把 end 翻成 `-axis` 的对照臂，
  它量出的正是 `u (0,-0.24,-0.97)` vs `(0,0.24,0.97)`（`v` 不变）——这条修复的直接证据。
- **"端面圆没有闭合，我想选择闭合"** —— 端面自己的那一圈椭圆**不是**外轮廓的一部分（轮廓只走可见的那一段，
  正面看就是胶囊的那两段弧），所以我原先根本没画它。现在按端面各自给了开关
  （`ShowStartRing` / `ShowEndRing`，**默认关**，保持包边那套观感）：打开就是**首尾相接的整圈**闭合环，
  用的是同一套 `PointAtStep` 采样角（所以环、十字、母线三者永远共顶点）。
- 现场读数行相应补上 `ringStart= / ringEnd=` 与两端法线来源（`normals=alongAxis/explicit`），
  以后"环没画"和"环画了但看不清"能分开说。

### 10.2 "拉近了有断口"＝我一段一段画线（2026-10-23 同一轮）

他放大看图时看到**线条在每个转角处有断口**。根因在我的调用方式，不在渲染器选型：库里
`CacheLineRendererBase` 的网格生成器会给**同一根线内的相邻子段**补"转角连接三角形"
（`LineMeshGenerator` 里的 `hasPrevInLine` 就是这个开关），而我原来对轮廓的每一段各调一次
`DrawLine` ⇒ 每一段都是"一根新线的第一段" ⇒ **每个转角都没有连接三角形** ⇒ N 段就有 N 个断口。
（端面圆环更明显：48 段 = 48 个断口，放大看就是"虚线环"。）

修法就是换调用形式：轮廓、两个端面圆环、十字都改成**一次 `DrawPolyline`**
（闭合的多边形/圆环靠"把首点补到末尾"实现闭合；十字改成"过圆心的三段折线"，
这样圆心处也有接缝连接）。母线本来就是各自独立的一段，仍然用 `DrawLine`。
**通用句：折线要用"一次提交整条线"的 API，别用"逐段提交"——接缝三角形是按"同一根线"补的，
逐段调用会把每一段都当成新的一根。**（这一层之后又被 §10.4 推进：**弧**不再用折线，改用曲线渲染器；
这里的"一次提交"继续适用于**直线**——十字与母线。）

### 10.3 单 Graphic 的 65535 顶点上限（下一轮修，他 2026-10-23 批准）

见 §8.8。他同意下一轮按顶点预算把网格**分块**成多个 Graphic。**同一个待定量的读数要一起做**：
他报"圆柱 `ShowFill` 打开即抛 65535"，但按代码算填充只有 ~4k 顶点（轮廓 ≤ 1024 面），
两者对不上 ⇒ 要么读数（`outlinePoints=` 与各 Graphic 顶点数）证明我算错，要么溢出的是别的元素
（开关只是触发了整块 canvas 重建）。**没有这个读数就不要下结论**（§8 的老规矩：零要说清零在哪一层）。

### 10.4 弧段改用曲线渲染器（他点名的 `Generation/Curve`，2026-10-23）

先给结论：**"拉近有断口"有两层，第一层是我的调用方式，第二层才是渲染器选型。**

- **第一层（已修）**：库里 `LineMeshGenerator` 的转角连接三角形只给**同一根线内**的相邻子段补
  （判据是 `hasPrevInLine`），而我原来对轮廓/端面环**每一段各调一次 `DrawLine`** ⇒ 每段都成了"新线的第一段"
  ⇒ 每个转角都没连接三角形。端面环 48 段 = 48 个断口，放大就是虚线环。
- **第二层（他指出的正解）**：折线渲染器**本质上**是分段直线，适合直线；**弧要用曲线渲染器**——
  `Packages/com.lrss3.deconstruction/Runtime/Generation/Curve`（`UICurveRenderer` / `CurveCacheRendererBase`
  + `CurveMeshGenerator`）内部就是**贝塞尔细分**，我只需要给控制点。他原话：
  "你现在用的折线渲染器就是分段的，适合用来显示直线……它的结构中就是使用的贝塞尔细分，完全不需要你自己实现。"

现在的分工：

| 画什么 | 用什么 | 为什么 |
|---|---|---|
| 轮廓的**弧段**、两个端面**圆环** | `UICurveRenderer.AddCurve`（三次贝塞尔，每节 ≤90°） | 弧必须是真曲线；细分交给渲染器，我只算控制点 |
| 轮廓的**桥接段**（跨端面那两条） | 同上，控制点取 1/3、2/3（直线贝塞尔） | 直线用贝塞尔表示就是直线，走同一条提交路径 |
| 端面**十字**、内部**母线** | `UILineRendererV2`（整条 `DrawPolyline`，不是逐段 `DrawLine`） | 他说的"折线渲染器适合显示直线" |

控制点全部由纯几何算，**每条都有能红的对照臂**：

- `TryParameterOf(disc, point) → θ`：解 2×2 反解椭圆参数并验 `cos²+sin²≈1`。**凸包分组**（哪几个点是弧、
  哪一段是桥）全靠它。臂 O 让它永远返回 false ⇒ 分组与"每点都有归属"两条断言同时红。
- `BuildArcPiece(disc, a, sweep, pieces, index)`：系数 <c>k = 4/3·tan(Δ/4)</c>（圆弧→贝塞尔的经典值）。
  **椭圆是圆的仿射像**，控制点随仿射变换同样变换 ⇒ 同一个 k 对椭圆弧一样成立。臂 P 把 `k` 置 0
  ⇒ 弧退化成弦，"中点鼓到弧上"那条断言红（这条正是"折线冒充曲线"的失败形状）。
- `ClassifyOutline` + 运行段合并：胶囊应当切成**恰好 2 段弧 + 2 条桥接**（探针钉住 `runs == 2`）。
- `SweepToDirection`：从"段内第二个点"定转向，凸包是逆时针，弧必须顺着走（否则会绕远路画一整圈）。

现场读数行再加一个 `curveEntries=`（这一帧往曲线渲染器提交了几节），
这样"曲线一条都没提交"和"提交了但看不见"能分开说。

### 10.5 端面环＝包边的**补弧**（他 2026-10-23 第二轮反馈）

他打开线框检查，报两条：
1. "关闭 `ShowStartRing/EndRing` 之后，消失的是**外侧**的圆环，但实际上我们应该控制的是**内部**的圆环闭合部分"；
2. "我们绘制的圆环好像是**重复**的……`showring` 的时候，原本的边框上会出现两次不同的线框"。

两条是同一件事：我把环画成了**整圈椭圆**，而包边已经画了那片端面的**外侧弧** ⇒ 外侧重了（同一位置两条线），
而"内部那半圈"才是这个开关该负责的东西。正解：**环＝包边那段弧的补弧**——起点接在可见弧的终点、
方向相反、扫过 `2π − |可见|`。于是外侧由包边画、内侧由环画，合成一整圈端面圆，两边都不重复。
包边整个关掉时，环自己补整圈（不然只剩半圈悬空，那才是"看不见的环"）。

**这里我连错两次（都留档，教训比结论值钱）**：

- 第一版把补弧写成"**把两个端点对调、再要求反方向**"。`SweepToDirection` 只会挑"同号里较短的那一条"，
  所以对调端点后它给出的是**原路返回** ⇒ 环又画回包边那一段，**和 bug 一模一样**。
- 第二版改成"起点接在可见弧终点、方向相反、扫过 2π−|可见|"。这仍然是错的：
  **反向走会把同一段弧原路覆盖一遍**（半圆时最直观：反着走一遍正好还是那半个圆），
  于是他看到的现象变成了"环补成了**外**半环"。
  **正解是同方向**：补弧＝从可见弧的终点**接着同方向**走完剩下的那一圈（`2π − |可见|`），
  于是可见弧 ∪ 补弧 = 整圈，两者**同号**、绝对值和 = 2π。

**为什么公式断言两次都放过了它**：我写的判据是 `|可见| + |补| = 2π`——**和实现用的是同一个（错误的）信念**
（"补弧 = 反向"），所以它两次都绿。真正抓住错误的是那条**几何**判据：

> `cylinder ring: the ring complement lies INSIDE the outline (inner half, not the outer)`
> ——补弧的中点用**点在轮廓内部**来判（可见弧的中点则必须落在边界上）。
> 实测把补弧写错时它报 `inside=True distance=7.9e-08 at (0,-10)`：
> 中点就贴在边界上（那是可见弧自己在的位置）。

**通用句：公式型判据和实现出自同一个念头时，两者会一起错；凡"某段几何属于哪一侧"这种性质，
要用一个**独立的几何量**去判（中点在哪、离边界多远、面积正负），别只比角度和。
** 对照臂 S「让环取可见弧的扫角」⇒ 这条几何判据红；臂 Q「`ComplementSweep` 改成 `return -sweep`」⇒ 公式那两条红。

## 11. 网格插槽、值模式、注册分组与绘制顺序（P7-P9，2026-10-23 他口述）

### 11.1 要解决的问题（都对着现行代码）

1. **面是靠枚举钉死的**：轴线存 `CubeFace`(0..5) + `Direction` + 三个比例，用 `m_FaceFrames[(int)Face]`
   取面帧（`ChartToolAxis.cs:46-51,191-194`），而面帧由 `XChartCubeGeometry.BuildFaceFrames`
   **硬编码六面**产出（`XChartCubeGeometry.cs:238-253`）。`XChartFaceFrame` 自己是通用的
   （四边形补丁 → 像素，不认识立方体），**被钉死的是生产者** ⇒ 换成异形网格（非六面、非四边形）就失效。
2. **网格分格与数据范围是两套口径**：分格数是手填 int（`XChartMeshBgConfig.cs:49`），
   没有任何东西从维度范围/刻度推出来（`XChartGridDivisions.cs:25-33`）——§8.2 那条"刻度与网格线对不齐"
   的根子就在这里。他要的是：**网格线由 chart 的数据范围统一控制**，工具只管自己的风格与细节。
3. **注册顺序与绘制顺序被一个数绑死**：工具平铺在 `[XChartTools]` 下，**sibling 索引就是绘制顺序**，
   而 `OrderIndex` 同时决定插入位置（`XChartToolsManager.cs:124-136`）⇒ "轴线要在点的上层"与
   "背景要先初始化"共用一个旋钮，互相打架。分组（背景/前景）在代码里不存在。

### 11.2 网格插槽（provider → consumer）

定义网格的**背景工具**在注册时把自己的一组组**标定顶点**开放出来（＝插槽）；要用这些几何的前景工具
（轴线、标尺、tooltip、可互动元素）按 **id** 取用，不再认"第几个面"。

- **板子**：`IXChartSlotBoard`（由 chart 建立、随 `IXChartRenderContext` 一起交给工具）：
  `Publish(id, mode, access, values)` / `TryRead(id, out SlotView)` / `Version`（值变了版本号前进，
  消费者据此重建）。板子是**几何**的通路，不碰数据（数据仍走 `IXChartDataSource`）。
- **一个 chart 只有一份"定义网格"**：网格工具是**定义工具**（`Definition` 分类，见 11.4），
  **在任何统一生命周期里它都第一个跑**——它先算好各维范围、格线与面片，其余工具（轴线、标尺、
  tooltip、可互动件）**通过 chart 找网格组件**（唯一网格时也可按 <b>0 号</b>登记，省一次查找）再取插槽。
  这不是"背景先画"，是**数据先算**：别人要用的东西在它们开跑之前就已就位。
- **一组顶点＝一个插槽**；消费者拿到的是只读视图（`ReadOnly`）或可写（`ReadWrite`：例如可拖动手柄
  写回去让网格跟随）。
- **异形网格**照样能用：它只要按同一套模式发布插槽；消费者读的是点，不是"面号"。
- **读的时机不绑初始化**：背景先初始化、前景后初始化，但插槽**每帧可读**（`Version` 变了才重建），
  所以"前景依赖背景"与"背景依赖前景发布的参数"（见 11.5）都不冲突。

### 11.3 值列表的"模式"声明（他给的四种起步）

模式决定"怎么切值 + 每个参数怎么解释"，**并声明读写权限**：

| 模式 | 值布局 | 一组代表 |
|---|---|---|
| `Line2D` | 2 值/点，2 点为一组 | 起点 → 终点（面内） |
| `Line3D` | 3 值/点，2 点为一组 | 起点 → 终点（立方体单位） |
| `Circle2D` | 2 值＝圆心，1 值＝半径 | 面内圆 |
| `Circle3D` | 3 值＝圆心，3 值＝法向，1 值＝半径 | 空间圆（斜切面） |
| `Quad3D` | 3 值/点，4 点为一组（ST00→ST01→ST11→ST10） | 空间四边形面片（**新增**：轴线要的是"面内 (s,t)→像素"的补丁，用两个 `Line3D` 组表达会依赖组序约定，不如单列一种模式） |

后续要曲线就再加模式（`Arc2D`：圆心 + 半径 + 起止角；`Bezier3D`：4 个控制点…）。
**模式是纯数据描述**：切值与解释都能在没有 Unity 的情况下断言。
每种模式都要能回答三件事（也各是一条判据）：**一组几个值**、**写进越界/个数不对时拒收**、**只读槽被写要拒**。

### 11.4 注册分组：初始化顺序 ≠ 绘制顺序

- **分类**：`XChartToolCategory { Background, Foreground }`（空间工具另算，它最先）。
- **初始化**：`Space → Background（按 RegistrationOrder）→ Foreground（按 RegistrationOrder）`；
  `RegistrationOrder` **默认＝注册先后**（没写也不会出现"顺序不确定"），显式值只用于同组插队。
- **绘制**：单独的 `DrawOrder`（默认＝注册先后），只决定 `[XChartTools]` 下的 sibling 顺序。
  "轴线的线画在点上面"＝调 axis 的 `DrawOrder`；而轴线**依然依赖网格发布的插槽**——两件事不再互相牵连。
- **统一调度**：管理器持有"按组 + 按 RegistrationOrder"的列表与"按 DrawOrder"的总表；
  `UpdateAll / RenderAll / Teardown / 报表` 一律**遍历列表**，不再逐个手调；新增工具＝进列表。

### 11.5 网格线由数据范围控制（11.1 第 2 条的落法，2026-10-23 他定的方向）

**定义权在网格，不在轴线**：网格是定义工具、最先跑，它

1. 从 chart 的数据板块**读各维范围**（`IXChartRenderContext.TryResolveDomain`；范围本身仍归维度行，§1 不动），
2. 由范围推**格线**（nice-step；`XChartGridDivisions` 那套按方向分格的算式保留），
3. 把**格线与面片**发布成插槽（`Quad3D` 面片 + `Line3D` 格线），

轴线**跟随**：读同一条格的插槽来定自己的刻度位置 ⇒ **"网格线与刻度逐条对齐"由构造成立**，
不再是"看着齐 + 手填分格数"（§8.2）。轴线原有的 `MajorCount` 变成"跟随网格"的默认 + 显式覆盖
（覆盖即放弃对齐，这是明说的取舍，不是静默）。读不到插槽时回落自己的分格数——
**并把这个回落印进报表**（零要说清零在哪一层）。

## 13. 折叠层级：默认全折叠 + 最深一层自动互斥（2026-10-24 他口述）

他的要求，逐条照做：

1. 所有折叠板块**默认处于折叠状态**；
2. "里面的一层折叠层"共用**一个排斥标记**——一次只想展开一个详细板块（"折叠太多了我看不到"）；
3. 要有**统一的标记**：先折叠所有被标记的，只留用户刚点开的那个；
4. 这个标记**只在最深的那一层**，"不是所有层级都需要这个东西"；
5. 层级本身要由**程序化的流程**生成，chart 自身和各组件都走同一套，互斥标记由流程自动补上。

### 13.1 落法

- **默认折叠**：`MakeGroup` 在没有历史记录时 `expanded = false` ⇒ 面板一打开只有「基础」「工具」两行。
- **层级不由调用方报数**（第 5 条的实质）：`MakeGroup` / `GroupFor` 只**登记**块，把 key 钉在盒子根的
  `userData` 上；整棵树灌完后 `FinalizeHierarchy` 把这一轮的块交给 `XChartPanelHierarchy.Compute`，
  现算 **父级 / 深度 / 是否最深**。**为什么不能传参**：一块挂在谁的 Body 里由 `GroupFor` 的合并规则
  决定（同名合并、跨父级不合并），传进来的层级会和真实挂接位置分叉——而第 4 条要的就是真实层级。
- **"最深"= 叶子块**：它下面再没有折叠块，也就是**真正装字段的那一层**。
  ⚠️ 这**不是**"全局最大深度"：一条分支只有一层（基础 → 调试），另一条有两层（基础 → 数据 → 维度 0），
  两边的叶子都算"它那条分支里最深的一层"，都要打标记；按全局深度挑会把「调试」漏成自由块，
  于是又能同时开两个详细面板了。这一条有专门的变异臂（M1）。
- **互斥只有一条**（第 2、3 条）：所有叶子块共用一组标记，展开任意一个 ⇒ 其余开着的一律收起；
  中间层（基础 / 工具 / 某个元素 / 数据）**不受管**——它们是导航，想开几个开几个。
- **「Expand」是显式例外出口**：`SetAllExpanded` 期间 `m_BulkFold` 屏蔽互斥。不屏蔽的话"全部展开"
  会**逐个开、逐个被收**，按下去只剩最后一个开着（等于没展开）。之后点任意叶子块，规则立刻回到"只开一个"。

### 13.2 机器看得见的与看不见的

- **看得见**：那套算术。`.ximage-gate/hierarchy_gate.py` 把实现文件**和探针一起编译**（不是抄一份），
  47 条断言：正本全绿，5 支变异臂各红在它指认的那条
  （M1 按全局深度 / M2 认生 `userData` / M3 一块不打 / M4 深度不累加 / M5 块块都打）。
  每支臂的 `WITNESS` 行印的是**它自己那份文件的字节与 sha**—— mutant 的身份不会被正本冒充。
- **看不见**：控件那一层。引擎的 mono **造不出真 `VisualElement`**（静态构造要绑
  `UIElementsRuntimeUtilityNative::VisualElementCreation`，实测 `SMOKE=THREW TypeInitializationException`），
  所以"假树"能验规则、验不了 `parent`/`userData` 到底接没接上。
- **因此面板自己印读数**：调试块一行「层级：块 N 最深 M 深 D ⇒ 判决」，报表的 `panel:` 行追加
  `groups= deepest= depth= hierarchy=`。两个判决名不是装饰：
  `HIERARCHY-NO-PARENT` = 块多于一个却没有任何块认到父级（往上爬那一格没爬到东西，互斥会连导航层一起管）；
  `HIERARCHY-NO-LEAF` = 一块最深都没有。这两条**不会**以"没打印所以没事"的形式蒙过去。

### 13.3 他侧验收（只需按一次 Ctrl+R）

1. 选中图表 ⇒ Inspector 只有「基础」「工具」两行（默认全折叠）。
2. 开「基础」⇒ 里面「基本信息」「数据」「调试」：开「调试」会把「基本信息」收掉（**它们同是叶子层**），

4. 再去开某个元素的「外观」⇒「维度 0」也收起 ⇒ 全面板任何时候只有一个详细块开着。
5. 按「Expand」⇒ 全开（横向比对的出口）；再点任意叶子块 ⇒ 回到"只开一个"。

## 14. 参数来源（P10）与桶采样虚拟化（P11）（2026-10-24 他口述的要求）

他的原话拆成四件可实施的事：

1. **每个工具的参数要能配"从哪个维度来"**——现在只有两种来源：配置里的常量，或硬编码的维度下标。
   需要一层统一的东西，把"工具要的参数 ← 数据维"配上，chart 才能真正驱动渲染。
2. 同一层要能和数据虚拟化结合：**折线按桶采样**，桶内算最大/最小/平均/中位数……，
   把一个范围的记录简化成**一个点**，取"我们认为最有意义"的那个统计量。
3. 有些渲染器要**复合数据**：一个项跨多个维度拼接（圆柱＝3 维 × 2 个值＝起点/终点；
   矢量场＝位置 3 维 + 方向 3 维）⇒ **渲染器按它实际需要的通道数创建项**，不由 chart 预设。
4. 65535 那条上限：折线靠**桶采样**解决；其他渲染器用**硬上限**或别的策略限制。

**同时改口径**：圆柱/散点/折线这些工具的数据来源与几何驱动**都基于 chart 的数据源**；
散点按当前维度定义给形态（2 维＝2D 散点、3 维＝3D 散点）；**"数据维数"不是"chart 是二维还是三维"的判据**
（以后可能上来四元数或别的表示）。chart 一般 3 维够用，但接口不该把它焊死。

### 14.1 P10 已落：几何来源＝常量 / 数据（先落圆柱）

- **纯算术单独一支** `XChartBindingMath`：三维取值、值域归一化，以及**记录编组**。
  四条"拒绝"分支都在渲染路径里，眼睛分不出"这一帧没画"和"画的是上一帧"，所以它们必须离线判：
  下标/维度越界、空数据、NaN 一律 false——**宁可这一帧不画，也不往几何里塞 NaN**。
- **顺序只留一个权威**（他 2026-10-24 的现场，问题是他改第 1 条而圆柱不动）：记录下标 `0` = 最早、
  `n-1` = 最新，**与数据窗口的行号同一套下标**；`XChartBindingMath` **不提供**"往回数第几条"这种相对量
  （第一版就是它：默认"上一条→最新"，于是同一份数据在窗口里是第 1 条、在工具里成了第 n-2 条，
  而末两条相等时圆柱两端直接合并）。API 是 `CompleteGroupCount` / `TryResolveGroup(recordCount, groupIndex, groupSize)` /
  `TryResolvePosition(data, recordIndex, …)`，全部**绝对下标**。
- **归一化是必须的一步**：常量坐标是立方体单位（±1），数据值是数据口径（可能上千）。
  `TryNormalize` 把值域映射到 ±1，**值域退化（min==max）时返回 false**（那一刻没有"数据在哪儿"），
  **超范围不裁剪**——超出盒子的值是数据的事实，裁了就看不出来了。
- **圆柱＝一组记录一根**（他纠正过一次：不是"最近两条"，也不是"n 条记录 n-1 根，而是两两一组 16 根"）：
  组 `g` 覆盖 `[g*size, g*size+size-1]`，两端取**组首与组尾**，组与组**严格不重叠、也不把上一组并进来**，
  凑不满一组的尾巴**不画**（记进 `groupsSkipped`）⇒ 32 条记录、组大小 2 = **16 根圆柱**（记录 0-1、2-3…30-31）。
  常量模式仍是配置里那两个坐标（`m_Start`/`m_End` 字段名与类型都没动，老预制体绑定不变）；
  新增字段只加在几何组里：`m_DriveByData` / `m_DimensionX|Y|Z` / `m_GroupSize`（默认 2）/ `m_MaxCylinders`（默认 64）。
- **多根的画家序**：三个渲染器（填充/曲线/折线）都只按**提交顺序**画，所以每帧把圆柱按深度
  **远→近**排一次（`ChartToolSpace.DepthOf` 越大越近）再提交；不排就会让近的被远的盖住。
  工具内部因此改成"各清一次 → 每根追加 → 最后统一提交"。
- **拿不到几何时的行为是明确的**：清空三个渲染器（**不能走绘制路径**——端面圆环吃的是上一帧的圆盘，
  会留下一个没有壳的环），并且**不退回常量几何**（那会假装数据在动）。
- **脏判定**把数据版本算进来：数据模式下图随数据变，只比 `ProjectionVersion` 会漏。
- **报表读数**：`geometry=literal | data(groups 16/16, size 2, rec 0->31, capped/skip 可选) | data-skipped(<原因>)`
  与 `cylinders=<这一帧真画了几根>`。理由是他那条老规矩：`skipped`、`literal`、"截断了多少"
  在画面上长得一样，只有印出来才分得清。

**离线证据**：探针 **323 项**（分组断言：32→16 组、组 0 = 记录 0-1、组 15 = 记录 30-31、
奇尾不成组、组大小 4 跨 0..3/4..7、负组号与组大小 <2 拒绝；下标断言：记录 0 / 记录 2（最新）/
越界与负下标拒绝；加上 NaN、归一化端点、退化值域、超范围不裁剪）；
`p4_control` 新增两支对照臂——「组多含一条记录」（`last = first + groupSize`）与
「尾巴组被放行」（`if (last >= recordCount)` 短路成 false），各红在点名断言；编译门三臂全绿。
**过程记录（值得留着）**：上一版探针首跑红在 `binding: a value outside the domain is NOT clamped`——
**是我手算的期望值错了**（`30` 在 `[-10,10]` 里映射到 `unit = 3`，我写了 `>3.9`），实现是对的。
期望值凡是手打的，都要对着真数据核一遍再写进判据。

## 15. Undo 删除时的原生崩溃：销毁窗口里不能再拆子孙（2026-10-24 现场）

**他报的**：删掉 chart 后撤回不了——一按 Ctrl+Z 就整个编辑器崩掉；之前界面上也看不到任何渲染内容。

**日志给出的因果**（`%LOCALAPPDATA%\Unity\Editor\Editor.log`，崩溃点在 482139 行），崩溃前 Unity 连报**两次**：

```
Child GameObject 'LineChunk0' was not registered into undo system and became dangling during an undo operation.
Use Undo.RecordCreatedObject to correctly add a child GameObject which can be handled by the undo system
   [StructureUndoBase.cpp line 600]
```

紧接着 `Received signal SIGSEGV`，56 层栈里关键那几层：

```
Object_CUSTOM_DestroyImmediate ← UnityEngine.Object.DestroyImmediate
  ← XChartToolBase.Dispose            (XChartToolBase.cs:88)
  ← XChartToolsManager.RemoveAllTools (XChartToolsManager.cs:166)
  ← XChartToolsManager.Dispose        (XChartToolsManager.cs:264)
  ← XChartBase.Teardown               (XChartBase.cs:509)
  ← XChartBase.OnDestroy              (XChartBase.cs:498)
  ← MonoBehaviour::WillDestroyComponent / GameObject::WillDestroyGameObject / PreDestroyRecursive
  ← ObjectUndo::ApplyUndo ← UndoManager::Undo ← Ctrl+Z（快捷键派发）
```

**机制**：Ctrl+Z 正在**应用撤销**（那条撤销就是把这个层级递归销毁）。Unity 在递归销毁途中回调我们的
`OnDestroy → Teardown`，而 Teardown 又对**同一棵子树的子孙**（工具根 → 池根 → `[XChartTools]` 根）逐个
`DestroyImmediate`——在 Unity 自己的销毁遍历**中途**再进一次销毁是重入，直接原生段错误。
`LineChunk0`（分块线渲染器建的子节点）没有登记进 undo system、成了 "dangling"，正是它把一条警告变成崩溃。

**修法（本轮已落）**：`OnDestroy` 先把 `m_HierarchyBeingDestroyed` 置真；Teardown 在这个窗口里
**一个 `Destroy*` 都不调**——生成物全是本对象的子孙，跟着一起没：

- `ToolManager.ReleaseBookkeeping()`：`RemoveAllTools(false)` → `tool.Dispose(false)`（该注销的账照记：
  先 `ForgetTextOwner` 再从列表里拿掉，只是不拆自己的根）+ 池只丢引用（`TextPool = null`）。
- `ToolsRoot` 只置空；"池根现拆现验"那条判据在销毁窗口里跳过（整棵子树都在被销毁，没有"漏一个"可言）。
- `XChartToolBase.Dispose(bool destroyRoot)` 与 `XChartToolsManager.Dispose(bool) / RemoveAllTools(bool) /
  RemoveTool(tool, bool)` 都带上了这个开关，**默认 `true`** ⇒ 非销毁路径（面板重建、「重新生成全部节点」）
  行为完全不变，`POOL-ROOTS-LEAKED` 那条判据继续有效。

**仍然开着的一条（警告，不再崩）**：生成物（`LineChunk*` / `FillChunk*` / `TextSlot_*` / 工具根 / 池根）
都没登记进 undo system，所以每次 undo 仍会印那句 "became dangling"。
要消掉就得在创建处 `Undo.RegisterCreatedObjectUndo`——但那会把生成节点塞进他的 undo 历史
（能一步步撤回出半死的图），**所以这条留给他定**，本轮不擅自改。

**恢复现场的事实（离线能查的都查了）**：

- **盘上的场景没坏**：`Assets/Scenes/Main_金塘.unity` 是完整 text YAML（71.9 MB、mtime 13:11）——
  崩溃发生在 Undo 中途，没来得及写盘。
- 但那份场景里**没有任何图表组件**（370 个 distinct guid 全扫过，`XChartBase` / `XMeshPreviewChart` /
  `XPseudo3DScatterChart` 三个脚本 guid 都不在），全 `Assets/` 的预制体里也没有 ⇒ 他那个 chart
  从来没被保存到盘上（是内存对象），"恢复"没有可恢复的源。
- `Temp/__Backupscenes/0.backup`（13:19，**二进制**）：我**判不了**它有没有那个 chart——
  guid 探针在这份备份上拿场景里 6 个真 guid 做对照也全是 0 命中，说明**这个仪器对二进制备份不可用**，
  不能把"没命中"读成"里面没有"（如实记档）。

## 17. P11：桶采样（把一个范围简化成一个点）（2026-10-24）

他的原话："linechart 渲染时需要以桶采样数据，每个桶里面还要最大、最小、平均、中位数……目的是把一个范围内的数据
简化为一个点，这个点则需要取一个我们认为最有意义的值去呈现。"

**落法**：新增纯算术 `XChartBucketMath`（`Runtime/XChart/XChartBucketMath.cs`）：

- `BucketCount(recordCount, targetPoints)`：目标点数 ≤0 或 ≥ 记录数＝**不聚合**（桶数=记录数，
  于是"没开桶采样"的行为与以前逐字节相同）；记录数为 0 时 0 个桶。
- `TryBucketRange(recordCount, bucketIndex, bucketCount, out first, out endExclusive)`：
  整数均分（`recordCount * i / bucketCount` 的整数算术），**桶与桶严丝合缝、不留缝不重叠、
  并起来正好覆盖整表**。
- `TryReduce(data, dimension, first, end, reduce, scratch, out value)`：桶内归约，
  直接复用数据层已有的 `XChartAggregateKind`（Count/First/Last/Min/Max/Sum/Mean/**Rms**/**Median**），
  不再造第二套枚举。NaN/Inf 一律跳过；整桶坏值返回 false——**宁可少画一个点，也不塞一个假位置**；
  中位数要么给够 `scratch`、要么拒收（渲染路径里不偷偷分配）。

**"最有意义"的默认值按元素定**：散点默认 `Last`（**抽稀**：取桶内最后一条真实记录，不造新值），
要看趋势就把桶内归约换成 `Mean`/`Median`、要看包络换成 `Minimum`/`Maximum`。
圆柱那条路是**记录编组**（§14.1：一组一根，端点取组首组尾），不是桶归约——两种不同的问题：
"把一段压成一个点"用桶，**"一段里取两端"用编组**。

**接进散点**（`ChartToolScatterPoints`）：`BucketTargetPoints`（0=不聚合）与 `BucketReduce` 两个参数，
配置里在"数据来源"组；`BuildPointsFromDataSource` 改成"算桶数 → 逐桶归约三路（+颜色维）→ 归一化"。
两个必须说清的细节：

- **归约不等于抽稀**：`Mean/Median` 得到的点**不在原始数据里**（是这段数据的中心），
  这是刻意的选择（"取一个我们认为最有意义的值"），默认给 `Last` 就是为了"不造新值"。
- **算完要裁掉尾巴**：渲染器**按数组长度**提交，桶数变少时不 `Resize` 就会画出上一轮的旧点
  （`TrimPoints` 干这件事）。

**上限这件事（他说的"65535 已经由上游分页解决了"）**：不再新造一套全局"预算÷每项顶点数"的换算——
上游分页兜住总量，剩下的**每渲染器上限就表达成它自己的参数**：圆柱是「最多几根」（默认 64）、
散点是「桶目标点数」（0=不限）。两者都会**在报表里印实际值**：
散点 `points= buckets= records= reduce=`、圆柱 `cylinders=` 与 `geometry=data(groups …, capped/skip …)`。

**判据**：探针 **343 项**（新增 20 条 `bucket:` 断言：桶数四态、7 桶切 100 条必须严丝合缝且覆盖末尾、
越界桶/桶多于记录数拒收、以及 5 种归约 + 中位数（偶数取中间两个的平均）+ 无 scratch 拒收 +
只读自己那段范围 + 空段/越界段拒收）**正本全绿**；`p4_control` 新增三支对照臂，**每条断言各有自己的生产者**：
「桶之间留缝」（首记录整体平移一格 ⇒ 红在 `contiguous`）、
「末桶早停一条」（只把最后一个 end 减一 ⇒ 红在"覆盖末尾"，而**留缝那条看不见它**）、
「Last 归约答成 First」（红在 `reduce Last … = 3`）。
**过程记录**：我第一版把"留缝"这条臂同时要求红两条，结果**覆盖末尾那条根本没红**——
末桶的 `end` 在那改法里根本没动，它看不到缝。**同一条结论的两半要各有各的变异体**，
不能拿一个变异体去担保两个不同机制。
**"桶采样的观感"（点够不够、`Mean` 是否比 `Last` 好看）归他在现场判**——离线只知道算术对。

## 19. P8：注册分组 + 注册序与绘制序分离（2026-10-24）

他 2026-10-23 的口径："定义一个值列表……需要一个 order 表示每个组件的刷新顺序……可以简化为直接使用
特定的类型标记，比如背景（背景网格），前景（参数点位、轴线标尺、tooltip、其他可互动元素）；
使用列表统一调度；这个 order 只是注册 order，**不是绘制顺序 order**，比如我希望轴线的线可以绘制在点的上面"。

**落法**（把"谁先算"和"谁盖谁"彻底分开）：

- **`XChartToolCategory{Definition, Background, Foreground}`**（`Runtime/XChart/XChartToolOrder.cs`）：
  定义组 = 空间、网格背景、立方体背景（它们算范围、发布插槽）⇒ **最先跑**；
  前景 = 散点/箭头/圆柱/轴线；`Background` 目前没有工具落在这里（位置留给"只画背景、不定义几何"的第三类）。
  分组是**类型标记**（工具 override `Category`），不入序列化——省一个要调的旋钮。
- **`XChartToolBase.DrawOrder`**（绘制序，小者先画）与 `OrderIndex`（注册序，小者先建/先算）**各管一件事**。
  配置里对应 `m_OrderIndex`（语义改为注册序）与新增的 `m_DrawOrder`；面板元素行现在是「注册序 / 绘制序」两个格子。
- **顺序规则只有一处**：`XChartToolOrder.Compare/Sort`（分组 → 数值 → **注册序**）。
  最后那一级是稳定性的来源——少了它，"值相同"的两个工具谁在前就看运气，画面上就是"有时点在上面、有时轴在上面"。
- **统一调度**：`XChartToolsManager.ApplyOrder()` 一次落两件事——
  **更新序**（分组→注册序，`m_Dispatch`）与**绘制序**（分组→绘制序 ⇒ 写进兄弟序，UGUI 按兄弟序画家序）。
  `UpdateAll` 走 `m_Dispatch`（所以定义组当帧先算完范围/发完插槽）；`RenderAll` 仍按注册表遍历（画家序由兄弟序决定，与遍历序无关）。
- **三个读数分开印**：每个工具的调试行有 `category= reg= draw= sibling=`——"谁先算"和"谁盖谁"必须能分开看，
  否则调错了也读不出来。

**同轮修的一处旧账**：`pnpm` 的时代里 `AddTool` 直接把兄弟序设成注册序的位置，于是"注册序 = 绘制序"被焊死；
现在兄弟序只由 `ApplyOrder` 按（分组、绘制序）写。

**判据**：探针新增 `tool order:` 断言（分组压过任何数值、背景夹在两者之间、同组比数值、
同组同值按注册序、自反相等、一次真实排序的置换、已有序时报"没动过"）；`p4_control` 新增两支臂
「先比值再分组」「丢掉注册序这一级」，各红在点名断言。

## 21. P12：数据的删、每列的范围，都收进数据窗口（2026-10-25 他口述）

他的原话要点（决定落在哪儿的是这些，不是我的排序）：

**21.1 一维范围：从"两端一起"改成"两端各问各的"**

- `XChartDimensionDefinition` 新增 `m_OverrideMin` / `m_OverrideMax`。`m_ManualRange` 的两个分量**总是留着**——
  没钉住的那端存的数不参与解析，但下一次勾上时格子不该是空的（"先填数再勾选"和"先勾选再改数"两条路都不能丢数据）。
- 旧的 `m_OverrideRange` 保留，含义＝"两端一起钉"，而且**只在两个分量确实不相等时**才算数（`LegacyBothPinned`）：
  "勾了但没填（0/0）不算覆盖"这条从 P4 起就在，它保护的是"默认状态凭空造出一段范围"，留在定义层，臂 A 仍能把它打掉。
- 分侧开关一旦写过就把主开关清零（`SetDomainOverride`）。不清就会留一个死状态：勾选框读出来是"勾着"（因为主开关），
  取消勾选却取消不掉——两个来源表达同一件事时必然出现的形状。
- 唯一的读取出口是 `DomainOverride`（`XChartDomainOverride{HasMin,Min,HasMax,Max}`）。**`EffectiveManualRange` 删除**：
  同一件事不留两个视图，否则"面板说的范围"和"工具用的范围"可以各自成立。
- 解析规则（`XChartDomainMath.TryResolve`，顺序就是优先级）：① 钉住的那端用填的数；② 没钉的那端用该维聚合；
  ③ 只钉一端而另一端连聚合都没有 ⇒ 以钉住的那端为中心展开 ±`DegeneratePad`；④ 两端都钉成同一个值 ⇒ 同样展开，
  而不是画一条零宽的轴；⑤ 手填把两端写反（或钉到聚合之外）⇒ **自动排序**，与旧规则同一处理；
  ⑥ 什么都没钉、聚合也没有 ⇒ `false`，调用者这一帧什么都不画（不是画在 0 上）。
- **入口收成一扇门**：`TryResolve(IXChartDataSource, dimension, out min, out max)` 自己读维度行 + 该维聚合；
  `XChartRenderContext.TryResolveDomain` 现在只是转发它，数据窗口的范围页与轴线的 `rangeSource=` 读数也走同一扇。
  以前"面板自己算一遍、上下文再算一遍"就是两处规则会分岔的地方（P4 现场那条 `NaN..NaN` 的读数就是这么来的）。
- 轴线的报表读数跟着改口径：`override[0..auto]` 表示"只钉了最小端"，`auto` 明确印出来——
  "这一端的数是谁给的"在画面上看不出来，只能在这行分。

**21.2 记录表：删一行、删一列**

- `TryRemoveRecord(index, out reason)`：越界就拒绝并报"现在一共 N 行"。**时间非递减不会被破坏**
  （去掉有序序列的一个元素还是有序的），所以时间窗的二分定位照旧——这条写在方法注释里，并有判据。
- `TryRemoveDimension(index, out reason)`：删定义 + 从每条记录的值数组里摘掉对应那一格。
  值数组的下标口径是**"第几个数值维"**而不是维度表里的行号——中间夹一个 Time 维时两者会错开，
  这条专门有判据（Time 在前、删第一个数值维）和一支把它按"维度表行号"算的对照臂。
- 删列**不回改工具绑定**（轴的 `Dimension`、圆柱的 X/Y/Z 都按序号绑）：这里只把数据的事实做对，
  序号前移的连带影响由窗口的消息点名（"后面的列号整体前移…要重新对一遍"）。
- 删列是破坏性动作 ⇒ 先把整表复制进剪贴板（和"清空"同一张安全网）再要一次确认；删一行不打断——
  一行就在眼前，且随时能整表导出。
- 范围覆盖的写入口是 `model.TrySetDomainOverride(...)` 而不是裸字段：**非有限数在门口就拒**
  （NaN/Inf 当范围端点＝整条轴安静地什么都不画，那是最难查的一族），写完 `Publish()`，
  于是按版本缓存聚合的工具下一帧就看到新域。

**21.3 数据窗口：两页 + 状态栏**

- 顶栏只剩动作：`导出 / 导入 / 清空 / 测试 / 强制刷新 / 绑定读数`。
- 中部两页（同一时刻只显示一页）：**数据表**（保持原来的精简样子）与**维度范围**；切换条是一条 `Toolbar`
  放在**窗口下面**（他说"在窗口的下面开一个新的分类出来"，不是把表变复杂）。
- 范围页一列一框、三层：① 列名 + **生效范围**（钉了哪端、没钉的那端跟数据）；② **统计**（样本数 / 最小 / 最大 /
  平均 / 中位 / RMS，全部来自 `TryGetAggregates`，与桶归用同一套聚合口径）；③ `钉住最小`＋格子、`钉住最大`＋格子（默认 0）。
  统计只读、覆盖可写，**各占一行**（他的原话"它是两个字段，就是两行，我单独去巡视它们"）。
- 每列那一框**不是折叠块**：范围页再套一层折叠没有任何东西可省（"数据面板不要搞太深了"）。
- 行的格子引用改挂在 `RowWidgets`（`cells.userData`）上，不再按 `cells[childCount - 1]` 数——
  加一列之后按位置数会把"标签"格当成数值格填。列表回收来的行控件如果格子数不对就**整条重造**（`EnsureWidgets`）。
- 每行末尾一个"删"，表头每列一个"×"，两者都占固定列宽（表头同一位置留空一格，否则列会错位）。
  （**P14 起**行末按钮改写作 `-`，见 §23；固定列宽那条不变）
- 状态栏右侧是「图表」引用字段；`EnsureChart` 的提示语跟着改成"底部状态栏右侧"（说错位置比不说更坏）。
- 范围页的统计**只在这一页真的露出来时算**：中位数要排序，在表格页每敲一下格子就为看不见的一页扫一遍全表是白付的代价。

**21.4 面板**

- 「数据」框整块删除：记录/维度/版本/已丢弃的读数、追加一条、清空、以及每维一行的显示名/可见/覆盖范围——

- §13 的层级/互斥判据不受影响（删掉的只是叶子块，互斥标记仍按"树上现算的最深层"打）。

**21.5 文本格式升到第 2 版**

- `XCHART-DATA 2` 的 DIM 行带 `覆盖标记(0/1) 覆盖标记(0/1) 最小值 最大值` 四个字段。
  第 1 版只带两个数，靠"相等＝没覆盖"表达"两端一起"，**分侧覆盖带不走**——导出再导回来会把
  "只钉最小"读成"两端都钉"，于是那一端被静默冻住。
- 第 1 版仍**读得动**，但版本只能来自表头：两种布局字段含义不同，v1 的 `-3` 落在 v2 的标记位上会被读成"没钉"。
  判据成对：v1 文件导入后两端仍是钉住的；v2 表头配 v1 的 7 字段行必须**报错**而不是静默少带一段覆盖。
- 顺手补两处门口：覆盖端点写 `NaN`/`Infinity` 直接拒；DIM 行字段数只接受 4 / 5 / 全套，"少一截"不再静默忽略。
  后一条原本是个**真崩溃**：老代码用 `fields.Length >= 6` 做守卫却去读 `fields[6]`，一条被截断的 6 字段行会
  `IndexOutOfRangeException`（探针以前只用 4 字段行测这条路，所以一直没撞）。

**21.6 两套下标：维度表的行号 与 值数组的下标**

写范围页时撞出来的另一件事：**"这一维"和"这一列"不是同一个号**。

- 维度表 `m_Dimensions` 一行＝一列（键、种类、显示名、范围覆盖都在那一行上）。
- 每条记录的值数组只装**数值列**（`NumericDimensionCount` 个格子）。表里全是 Number 时两个号重合；
  夹进一个 Label/Time 列（导入的文本、雷达那种带标签的维度都可能带）就**错开**。

三条规则收进一个纯函数文件 `Runtime/XChart/XChartColumnMath.cs`（`ValueCount` / `ValueSlot` /
`DefinitionOfValueSlot`），模型与窗口都调它：

- `XChartDataModel.NumericDimensionCount` ＝ `ValueCount(表)`（原来自己数一遍）。
- `TryGetDimension(dimension)` / `TrySetDomainOverride(dimension, …)` 的入参是**值下标**——
  与 `GetValueAt` / `TryGetAggregates` 同一个口径，因为工具绑的就是这一个数。
  按表行号回答会在混合种类的表上把"第 1 维"答成 `tag` 那一列，于是钉住的范围落到一个工具根本不读的列上。
- `TryRemoveDimension(tableIndex)` 的入参是**表行号**（窗口"×"按钮就在那一列上），
  它内部用 `ValueSlot` 决定要不要摘一格——非数值列返回 −1，本来就没有格要摘。

窗口的两处跟着改：**范围页一列一框**，标题同时印出两个号（`列 2 · Y（值下标 1）`；**P14 起收成 `Y [1]`**，见 §23），
非数值那一列印"这一列不占值格"并把两个勾选框禁掉；**表里的格子**记住自己对应的值下标
（`RowWidgets.Slots` 是这套分布的签名，行控件回收时签名不对就整条重造——只看列数的话，
换一张同列数、种类不同的图会把不可编辑的格子当成能改的）。

判据：`column maths:` 5 条（值下标 1 在 `[x, tag, y]` 上找到的是 `y`；不占值的行报 −1；
门用第二列自己的聚合解范围；钉第二列的最小端只动第二列；第一列不被第二列的钉影响），
配 4 支臂：值计数把非数值列也算进去、门按表行号答维度、表行号的"值下标"就是行号本身、
以及"每个值下标都答第一个数值列"。

`data cut:` 删行删列 7（含 Time 维夹在中间那条）、`column maths:` 下标口径 5、`data text:` 格式形状 4 + 往返 2 改写）。
`p4_control` **47** 支臂每支红在自己点名的断言上，本轮新增/改派 13 支：主开关的等值规则被删、门不读维度行、
解析器不走"没钉"分支、没钉的一端仍取手填值、无限聚合当可用、非有限覆盖值被收、删行没真删、
删列留着被删的那一格、值下标按维度表行号算、导出丢掉最大端标记、v1 文件按 v2 布局读、截断的 DIM 行被放行、
值计数把非数值列也算进去。门三臂（runtime / player / editor）绿；`p2_control`、`pool_family`、
`generator_gate`、`hierarchy_gate` 同轮复跑。

**判据的判据（本轮抓到的两条，属于同一族）**

1. **`Expect(label, cond, detail)` 的 detail 是无条件求值的。** 我在一条说明串里直接写了

## 22. P13：立方体那几件搬进「工具」，格线只有一个作者（2026-10-25 他口述）

### 22.1 现场报的四条，逐条要对得上机制

1. 「显示网格线」勾选后网格线**反而消失**，不勾反而在；默认是"勾着 + 看得见"。
2. 保持它关闭，**再去操作别的**（转一转让表刷新）网格线又不见了／回来再点又显示出来——"总之有 bug"。
3. 「立方体外观」这一组还挂在 `基础` 下；而且面板说"另有脚本注册的工具 3 个"却**不说是哪三个**。
   他的要求原话：既然是工具就要放在工具下面，chart 本身应该只留 `基础`。
4. 添加的 `Mesh BG` 元素里**填充面改了没作用**（Nothing／Everything 一模一样），网格面有效，
   但它和图上那两个开关**互相冲突**，"逻辑上就很冲突，很割裂"。另外名字要改成描述性的
   （`BG Cube Grid`），因为后面还有平面坐标系网格、雷达图网格、神经图谱网格。

### 22.2 根因：同一件事有两个作者

`ChartToolCubeBg`（线框）当年不只画 12 条棱，还画**面内格线**，并且把格线发布成
`mesh.face.<n>.grid.S/.T` 插槽；`ChartToolMeshBg` 也画格线、也发布**同一批 id**。两件事由此发生：

- 插槽板按 id 覆盖 ⇒ **谁后跑谁说了算**。轴线"跟随网格"跟的是最后发布那一家。
- 两家的条数算式不一样：线框那侧画 `i/(N-1)`（含两条边共 N 条），网格那侧画 `d/divisions` 的**内部线**
  （N−1 条）。于是关掉一边，另一边把那批位置**用另一套条数**画回来 ⇒ 看上去就像复选框接反了（症状 1）。
- 图上还有一个 `m_ShowGridLines`（只管线框那半），元素上另有一份 `GridFaces` 掩码（只管网格那半）。
  一个开关只能管半个作者，另一半在别的时机（刷新、重投影）亮回来 ⇒ 症状 2 的"状态会跳"。
- 面板上「基础 → 立方体外观」那组字段与元素表里那份配置**存的是同一件事**，两处各一份、
  谁后灌谁赢 ⇒ 症状 3、以及症状 4 的"割裂"。

本项目里这类死法已经出现过好几轮，形状都一样：**两处存同一件事**。这轮的处置不是给某个开关补个取反，
而是把"谁画格线"这件事变成**结构上只有一个作者**。

### 22.3 现在的分工（一件渲染活只有一个作者）

| 元素（面板上的名字） | 画什么 | 发布什么插槽 | 手里有哪些旋钮 |
| --- | --- | --- | --- |
| `Space` | 不画 | — | 四元数、半边长、尺寸口径、中心偏移（**唯一投影权威**） |
| `BG Cube Wire` | 12 条棱（前向／后向两套色） | `mesh.face.<n>` 四角 | 前/后棱颜色、棱宽、显示后向棱 |
| `BG Cube Grid` | 面填充 + 面内格线（+可选面轮廓） | `mesh.face.<n>` 四角、`…grid.S/.T` | 填充面掩码与双色、网格面掩码、格线色/宽、分格数（统一 + S/T）、绑定的维度、只画可见面 |
| `ChartTool_ScatterPoints` | 点 | 刻度插槽 | 形状、大小、描边、颜色映射 |

三条硬约束：

- **线框没有"格线"这条代码路径**（字段、渲染器、发布全删了）。不是"默认关着"，是**不写它就无法画**——
  两个作者的形状从此表达不出来。
- 网格元素**画上去的线**用的就是**发布给轴线的那份比例数组**（`PublishGridSlots` 算完留在
  `m_RatioScratchS/T`，`DrawGrid` 直接读），不再各按各的条数算第二遍。
- **"哪些面有格线"也只有一个判据**：发布侧与绘制侧共用 `DrawsGridOnFace(face)`
  （掩码 ∧ 面帧有效 ∧（开了"只画可见面"时）朝向观察者）。此前发布是**六面全发**的，
  于是掩码筛掉的面照样有插槽，轴线会去吸一条画面上一条都不存在的线——同一个病换到了插槽那一层。
  等式现在由工具自己判：报表印 `faces=画上/发出`、`retracted=`（这一轮撤掉了几个面的格线插槽）与
  `linesCheck=ok|DIFF drawn=… want=…`（期望值 ＝ 发布的条数 ＋ 描轮廓的面数 × 4；轮廓那 4 条只画不发）。
- **板子因此多了"撤下"这一面**（`IXChartSlotBoard.Unpublish(id)`）：只有 <c>Publish</c>（同 id 覆盖）的话，
  定义者说得出"这里的线换成这一批"，却说不出"<b>这里不再有线</b>"——上一轮那批值会一直挂在板上被轴线吸走。
  掩码筛掉的面、以及整个网格元素被 Dispose 时，都会把它发过的 12 个格线插槽撤干净
  （**只撤自己发的**：`mesh.face.<n>` 那批四角是立方体本身的几何，线框元素也在发，动它就是拆别人的定义）。
  空数组发布是拒的（组数必须为正，§11.2），所以"撤下"只能是一个显式动作而不是一次空写。
- 分格数按方向分（统一值 + S/T 各一份，0＝跟随统一值），因为两条轴的刻度数通常不同；
  等分时"沿 S 的线由 **T** 的分格数决定"（算式只在 `XChartGridDivisions` 里，探针钉着）。

### 22.4 渲染参数搬进元素表：预设自己声明默认元素

他给的方向是"chart 默认情况下就是个网格、纯数据，所有的渲染都是基于工具的；创建脚本时就该带上特定工具，
注册可以直接在配置里注册"。落法：

- `XChartBase.DeclareDefaultElements()`：派生类在这里声明"这张图默认带哪些元素"（规范意义上的**配置注册**）。
  `XPseudo3DScatterChart` 在这里给出 `Space` / `BG Cube Wire` / `BG Cube Grid` 三件。
- `AddDefaultElement<T>()` **按类型去重**（`XChartElementTable.IndexOfKind`，纯函数、离线可验）。
  图表初始化会跑很多遍（域重载、预制体开合、进 Play），不去重就是每遍多一个背景 ⇒ 格线画两遍、
  边越描越粗，现象只会被描述成"图越来越糊"。
- 只在**第一次读到这张表**时补（`m_ElementsSeen` 标记）：他把某个元素删掉就是意愿，之后不再自动补回来。
  老场景的表里往往只有轴线/散点（立方体那几件当时还是图上的字段），第一次进来会把缺的补上——
  否则这次改动就变成"升级完背景整块没了"。
- 图上那组「立方体外观」字段**删除**。`CubeHalfSize` / `Rotation` / `ApplyViewPreset` / `FrontEdgeColor` /
  `GridDivisionsS` / `ShowGridLines` … 保留为**转发属性**：读写的是元素表里那份配置本身
  （`ElementOf<XChartSpaceConfig>()` 等），写完立刻 `ReapplyElements() + ForceRefresh()`。
  属性还在（外部脚本不必修），但**状态只有一份**了。元素被删掉时 getter 给中性值、setter 静默不做——
  不抛，也不背着他造一个元素回来。
- `ShowGridLines` 的真身是 `BG Cube Grid` 的 `GridFaces` 掩码：开＝六面都画，关＝一面都不画。
  只画后墙那种"部分面"直接用掩码，别再用布尔。
- 网格元素的默认值就是旧「立方体外观」的默认行为：不填面、六面都画格线但只画朝向观察者的那几面、
  不描面轮廓（轮廓归线框那 12 条棱，描两遍只会让边变粗）。

**代价要说明白**：字段被删 ⇒ 场景/预制体里存过的那组立方体外观值会静默回到默认（Unity 按字段名恢复序列化）。
姿态、半边长、格线颜色要重拧一遍。这是"两处存同一件事"必须付的一次性账。

## 23. P14：数据窗口的界面收敛（2026-10-25 他现场三条）

他对着窗口截图点的三条，都是"界面上话太多、而话多的地方还压掉了该看的行"：

1. **行末删除按钮**：`删` → **`-`**（固定列宽那套不变；表头同一位置仍留空一格）。
2. **范围页的号**：`列 2 · Y（值下标 1）` → **`Y [1]`**。行的**位置**已经是表里的列号，
   括号里再报一遍号只是把同一件事说两次；`[n]` 就是工具真正使用的那个数。
   不占值格的列印 `tag [-]` ＋一行 `不占值格`。统计行去掉 `统计：` 前缀；
   生效行不再复述"哪一端被钉住"（**下面那两个勾自己就是读数**）。
   状态栏的回执从"我改了什么"改成**结果**：`Y [1] 生效 -100 .. 100`。
3. **说明文字退回 tooltip**：`kListHint` / `kRangeHint` 都只浮着不占界面。范围页那段可见的长说明删掉，
   其中"这正是“原点必须留在 0”那类要求的做法"这类句子**是开发时我们俩的对话，不是界面文案**——
   它对着当时的我，不对着下一次打开这个窗口的他。要么写成一句操作帮助（tip），要么就别写。

**第一列挤成一行的真机制**：不是"少写了一行"，是**那一整页的容器允许收缩**。
UI Toolkit 里 `flexShrink` 默认为 1，窗口矮了，被压扁的就是**最上面那一行**——三行的框塌成两行、
文字叠着画；后面几列因为剩余空间够才看起来正常（所以他看到的是"只有第一列坏了"）。
⇒ 修法是从 `ScrollView.contentContainer` → body → 每列的框 → 框里每一行**整条链 `flexShrink = 0`**，
标签一律 `NoWrap`：装不下宁可截断，也不许和邻行叠在一起。表头那一行同样补 `flexShrink = 0`
（它被压一次就会整表错位）。

**判据与账**：编译门三臂绿（编辑器程序集里 `XChartDataWindow.cs` 是点名源，"门绿"包含它编过了）。
但这三条**全是观感，离线判不了**（引擎 mono 造不出真 `VisualElement`，§13.2 那条实测仍然成立）
⇒ 布局是否真的不再叠行、文案是否够短，**归他现场判**；P14 没有任何一条绿可以替"界面已经对"说话。

  `AppendHeaderGroups` 会把它们整组塞进元素 Body 的「其它」里 ⇒ 标题行有了 √ R D 之后，同一个写入口
  就出现两次。现在这三个名字在元素分组时被跳过（与 `m_SlotId` 同一条规矩：同一件事不做两个入口）。
  **P17 追加**：`m_OrderIndex`/`m_DrawOrder` 也不再在 Body 里留输入控件（§24.5 的政策）。

### 24.2 默认元素（`Space` / `BG Cube Wire` / `BG Cube Grid`）**让删，也让关**

删掉就是"这张图我不要它"，那是他的意愿，面板不该拦（同 §22.4：预设只在第一次读到这张表时补齐缺的那几件，
之后不再自动补回来）。三个各删掉会怎样，逐条说清，不留"删了会怎样？"这种没答案的格子：

| 删 / 停用 | 结果 | 为什么不会连锁 |
| --- | --- | --- |
| `BG Cube Wire` | 没有 12 条棱 | 面四角仍由网格元素发布 ⇒ 轴线照旧有宿主面 |
| `BG Cube Grid` | 没有填充、没有格线 | 面四角由线框发布 ⇒ 轴线照旧；`AlignToGrid` 回落，报表 `align=` 说原因 |
| `Space` | 回到默认姿态 | 见 24.3：不变量补全之后，删掉它不等于图没了 |

⇒ `[-]` 与 `√` 对**每一个**元素都保持可用，不做"某几行不许删/不许关"的特例；他问的"如果不能删就把 `-` 禁用掉"
这一支因此不落地，理由就写在 `-` 的 tooltip 里。

### 24.3 顺带补全一条不变量：`EnsureSpace()` 现在**每次重建后**都跑

⇒ 投影权威为 null，线框/网格/散点全部不画，现象是**"整张图突然空了"**——而这只是点了一下"删"。
补上之后：删掉空间元素＝回到默认姿态继续画（旋钮没了，重新 Add 一条 `空间（基变换）` 就回来）。
这条**离线判不了**（要真 `GameObject` + `ToolManager`），判法归现场：删掉或停用 `Space` 那一行 ⇒ 图还在。

### 24.5 序号的政策：注册序**只读**，绘制序**跟着位置走**（2026-10-25 他第二轮澄清）

他原话（意译后按代码语言记档）：**"我根本不想给它设置这两个序号"**——

- **注册序**：由**类型**定好的（定义几何的那一类天然靠前，数据呈现那一类天然靠后）。
  它对人只在"看"的意义上存在：面板**只显示、不可编辑**。用户手填注册序没有意义，
  写错了还会把"谁先算"这件事弄乱；所以它不进任何输入控件。
- **绘制序**：**绑定元素在表里的位置**——调上移/下移不仅仅是改层级顺序，**它就是改绘制顺序**。
  于是不再有第二个手填的绘制序号，也就不存在"位置和序号各说一套"。

⇒ 落法（面板侧）：标题行上的 `R… D…` 是**文本读数**（他第一轮就是这么要求的，我第一轮理解成输入框，
错了）；`m_OrderIndex` 在面板上**不再出现输入控件**（从"其它"组里跳过，原因见 24.1 那条备注）；
`m_DrawOrder` 同样不出现——上移/下移按钮直接把它写进去，面板只把结果印成 `D…`。

**为什么这比"可编辑"更强**：序号一旦能手填，就会出现两条口径（位置 vs 数字）指向不同的事实，
"上移之后绘制顺序到底变没变"这个问题就没人回答得了。绑定之后**位置是唯一权威**。

**落法（代码侧，2026-10-25 同日）**：面板的 `AfterStructureChange()` 里调 `RenumberDrawOrder()`——
任何结构变化（上移/下移/加/删）之后把表内每个元素的 `m_DrawOrder` 重写成它的位置（0,1,2…）。
于是"位置更靠后＝绘得更晚＝盖在上面"。面板上 `R… D…` 只是这两个数的**读数**（`RefreshOrderReadouts` 就地刷新）。

**终态（2026-10-25，交付树上复跑那一跑）**：`p4_control` **52/52** 支臂各红在自己点名的断言上；
探针 **424** 项 **0** 失败；`p2_control` 4 臂、`pool_family`、`generator_gate` 2 变异、`hierarchy_gate` 5 变异全绿；
编译门三臂 + 3 支对照绿。产物：`.ximage-gate/` 下 `gate_p15b.txt`、`probe_p15.txt`、`p4_p15.txt`、
`chain_p15.txt`（每套一个 `*VERDICT rc=` 行）。
**注意这份绿覆盖的是什么**：它覆盖的是**算术与协议那一层**（`EnsureSpace` 那条不变量在不在，
它一句都看不见）——那条只有现场"删掉 Space 那一行，图还在不在"能判。

**覆盖范围要说准**（这一轮收口后又动过一次文件）：52 支臂 / 探针 / p2 / family / generator / hierarchy
那一次复跑覆盖的是"标题行 + `EnsureSpace`"那棵树；之后为拆掉「其它」里的第二入口又改了一次

## 25. P17：矢量场（箭头）——数据口径（**2026-10-25 他澄清后定稿**）、相对/绝对、连续绘制、颜色

> **口径修正（同一天，先听他澄清）**：本节初版把矢量场写成"一条记录装两组三维（6 维）"，那是照着
> 旧实现/旧文档推的，**不对**。他给的正确口径是：**三维就是坐标本身（跟圆柱一样用 x/y/z），
> 一支箭头由相邻两条记录构成；颜色接在第 4~7 维**。代码随后按这一版改（改前它仍按旧口径跑）。

### 25.1 现场：加了箭头一条都不画，根因是"形状不够时静默返回"

他加了「向量箭头」元素、数据也在，一条都没出现。原因是一行判断：
`if (NumericDimensionCount < OriginDimension + 6) return;`——算完 0 支、提交 0 个面，
画面上与"工具没注册 / 空间是 null / 渲染器没建"**完全同形**，报表里也只是几个 0。

⇒ 处置不是改那行判断，而是**让这件事说得出来**：

- 元素配置报出自己的需求（`RequiredNumericDimensions`），面板印一对数：
  `需要 N 个数值维，表现在有 M 个　⇒ 一条都不画（报表里 dims=N/M）`；
- 报表里该元素自己印 `dims=有/需要 arrows=算了几支 mode=… colors=…`。
- 需求由**元素自己的配置**报，面板不写特例——下一个元素不用再写一遍，两边也不会分叉。

### 25.2 数据口径（定稿）

一条记录 **7 个数值维**，前三维与圆柱同义：

| 维 | 含义 | 必填 |
| --- | --- | --- |
| 0,1,2 | **坐标 x/y/z**（立方体单位，与圆柱、散点同一套归一化） | 是 |
| 3,4,5 | **颜色**：色相（**0..256 色环**）、饱和度（0..1）、明度（0..1） | 否 |
| 6 | **不透明度**（0..1） | 否 |

**一支箭头 = 相邻两条记录**（第 i 条与第 i+1 条）。他原话："我们是 0 和 1，一个代表坐标，
一个代表它的矢量的方向"——即两条记录一组，而不是一条记录里塞两组三维。

- 为什么相邻而不是像圆柱那样"严格不重叠分组"：圆柱要的是**一段一段的杆**（组与组不共享端点），
  矢量场要看的是**相邻两点之间的关系**（首尾相接才连得起来）。
- 颜色是**每条记录自带**的 ⇒ 一支箭头的起点色与终点色可以不同（沿杆渐变）。
  这是他说"两个分量都可以独立设置颜色，从而组成七维信息"的落点。

### 25.3 两种读法：相对 / 绝对

| 读法 | 第二条记录怎么用 | 算式 | 螺旋数据画出来 |
| --- | --- | --- | --- |
| `Absolute`（默认） | 它的**坐标**当作方向矢量 | 起点 + 方向×倍率 | 每根朝"下一点的坐标方向"散开＝一片**刺猬** |
| `Relative` | 它是**第二个点** | 起点 + (第二点−起点)×倍率 | 一串**首尾相接**、顺着螺旋转 |

算式收进纯算术 `XChartVectorFieldMath.Tip(mode, first, second, scale)`，离线探针钉住
（含"同一份数据两种读法必须给不同的末端"——这条要能红，否则两种读法等于同一种）。

### 25.4 连续绘制，以及"勾一个、藏一片"

`Continuous`：把每条记录的坐标**按顺序连成折线**（只有最后一段带箭头）。
这时"相对/绝对"没有意义——连起来的本来就是空间里的一条路径 ⇒ 面板上那两个选项**隐藏**。

互斥显示的判据写在配置自己身上（`XChartElementConfig.IsFieldHidden(fieldName)`），
面板只负责"照着藏/放"。**藏而不是不建**：面板树在值变化时不重建，勾回来必须立刻可见。

### 25.5 颜色（可选维）

第 4~7 维 `[色相, 饱和度, 明度, 不透明度]`：

- 色相走 **0..256 的色环**（256 与 0 同色，128 是半圈）；其余三个按 0..1 夹住。
- **不透明度那一维不算硬需求**：多给就多读、没给退回单色 alpha。算进门槛的话，
  勾一下"有不透明度"会让整个元素因维数不够突然消失——那是一个开关变成了总闸。
- 不是有限数**门口就拒**（退回单色，不画成黑）：NaN 经取模 + HSV 换算会变成一块"看着像黑"的东西，
  那是我们替数据编的颜色。
- 换算**自己写**（`HsvToRgb`）而不是调 `Color.HSVToRGB`：后者是引擎侧静态调用，离线探针跑不起来，
  而这条换算正是要离线钉住的。

### 25.6 示例数据（"点一下就能看到东西"）

测试数据 `螺旋矢量场`：一圈正弦/余弦点，每条记录 7 维（坐标 + 色相 0→256 走满一圈 + 饱和度/明度 1）。
**它自己会把列补到 7 个**——测试数据的判据是"能用"，不是"提示他先去加四列"。

## 26. P18：矢量场的两端颜色，与"路径上的箭头"（2026-10-26）

### 26.1 两端各自的颜色＝填充四边形多一档线性渐变

> **本节那一档"箭头用法"已被 §29 撤掉**（2026-10-26 他纠正：杆走线、头用曲线渲染器的原生标记）。
> `AddFaceLinear` 这个能力留着——它是填充渲染器自己的一种上色模式，只是箭头不再经过它。

`XChartMeshFillRenderer` 原来只有两档：四角同色（平坦）与"四角 + 中心"（径向）。这轮加第三档
**线性渐变**（`AddFaceLinear`）：`00/10` 一对边一色、`01/11` 一对边一色，渐变方向垂直于这两条边。

- **每面花几个顶点收成单一定义** `XChartMeshBudget.VerticesPerFace(kind)`：预算侧与写顶点侧必须同源，
  否则会出现"预算以为 4 个、实际发 5 个"，恰好在卡线时撞 65535（§10.3 那一族）。
- 箭头：**杆走线性渐变（起点色 → 终点色），头走单色（终点色）**。两端颜色来自相邻两条记录各自的颜色维，
  所以"这条记录的颜色和下一条不同"就直接看得出来了。
- **杆的四角绕序有判据**：`BuildShaft` 把 a/d 放在起点一侧、b/c 放在末端一侧——配错的话画面上是
  "杆的两侧各一色"而不是"沿杆渐变"，这种错最容易看漏，所以离线钉住（探针 `arrow shaft:` 一条 + 一支臂）。

### 26.2 连续绘制改走曲线渲染器（贝塞尔细分）

路径是"会弯的线"，所以交给库里的 `UICurveRenderer`（圆柱弧段同一件，§10.4：折线渲染器只留给直线，
逐段提交会在转角留断口）。API 形状是从我们自己的调用点学的：
`AddCurve(CurveCacheEntry{startColor,endColor,tessellationSegments}, 4 个控制点, 4 个宽度)`，
`autoRebuild = false`（控制点每帧由工具喂），报表读 `LiveVertexCount`。
**entry 自带起止色 ⇒ 沿程渐变是曲线渲染器本来就有的能力**，路径的颜色不必靠切段去凑。

途经点 → 控制点用 **Catmull-Rom 转三次贝塞尔**（张力 1/6，`XChartArrowPathMath`）：
这样曲线**真的经过每个数据点**——矢量场的点是数据本身，用不经过控制点的自由贝塞尔等于把数据挪了位置。

### 26.3 箭头位置可调：路径在剪口处剪断

`HeadPosition`（0..1，默认 1＝末端）＝"画到路径的哪个位置"，箭头放在那一处：

1. `ResolvePosition(段数, along)` → 段号 + 段内参数；
2. 该段用 `Split` 在参数处剪成两半，**只画左半**（前面的段整段画）；
3. 箭头放在剪口上，方向取该点的**切线**（`Tangent`），不是两端连线——弯处会歪。

**为什么要剪断**：不剪的话路径从箭头底下穿出去，看着像"箭头朝里长"。
剪开再接回去必须与原段逐点一致（探针 8 个采样点，最大偏差 <1e-4），否则"箭头前面那段路挪了位"。

### 26.4 互斥显示又用了一次

`HeadPosition` 与 `PathSegments` **只在连续绘制下出现**（一支一支画时头永远在末端，这两个值没有意义）；
`VectorMode` 反过来只在非连续下出现。判据全在配置自己的 `IsFieldHidden` 里，面板不写特例。

### 26.5 读数与退路

报表那一行现在带 `path=curve|fill|-`、`at=<位置>`、`curves=<提交了几段>`、`curveVerts=<顶点数>`：
**曲线渲染器不在位时退回直线段**（形状仍读得出来），但退没退在 `path=` 上一个字就说清了——
不是"悄悄换个画法还报一样的数"。

## 27. P20：外部数据驱动访问（"我能不能直接拿到圆柱渲染器，改属性就自己更新"，2026-10-26）

### 27.1 他要的形态（原话）

> 我是否有方法可以直接 GetChartComponent&lt;Cylinder&gt; 去获取这个圆柱体渲染器。并且访问里面的所有属性字段，
> 然后设置的同时，属性就会自动完成脏标记，这样就能完成渲染组件更新了。

本轮之前只有第一半有：入口早就在（`chart.ToolManager.FindTool<ChartToolCylinder>()`，`XChartToolsManager.cs:257`），
第二半没有——工具的参数全是裸自动属性，**写进去值在、画面不动**，必须再补一句 `MarkDirty()`
（`XMeshPreviewChart.ApplyVolume` 就是手工补的那个样子）。

### 27.2 三条入口，各管一件事

| 要改的东西 | 入口 | 怎么生效 |
| --- | --- | --- |
| 数据（记录、维、范围覆盖） | `chart.DataModel` / `chart.DataSource` | 版本自增，下一帧自己刷（一直是自动的） |
| **渲染元素的参数** | `chart.Tool<ChartToolCylinder>()`、`chart.Space` | **setter 自己置脏**，下一帧重算几何 |
| 元素的结构与作者数据 | `chart.Elements` / `chart.Element<T>()` | 改完要 `ReapplyElements()` / `RebuildElements()` |

`Tool<T>()` 是 `ToolManager.FindTool<T>()` 的空安全简写（管理器还没建时答 null 而不是抛 NRE——
"图里现在有没有这一类"是现场状态，调用方要问得出"没有"）。同类多条按名字点：
`chart.Tool<XChartToolBase>("Axis 2")`，名字就是 `ElementNameFor(i)` 那一个。

### 27.3 权威只有一处：配置是作者数据，工具是它的投影

外部写进**工具**的值，会活到下一次 `ReapplyElements()` / `RebuildElements()`——那一次把配置整份重灌进工具
（面板动任何一个字段、增删/停用元素、脚本重载、进 Play、`ResetRender()` 都走这条路），
于是外部的写被**静默覆盖**。这不是缺陷，是"两处存同一件事"那一族的取舍：

- 只要求这一帧看起来对 ⇒ 写工具（本轮就是为这条把 setter 做成自动置脏的）。
- 要活得过重建 ⇒ 写配置；配置的公开写入口还没开（27.6），现在写它得走 `SerializedProperty`。
- 反向那条（把元素当前状态收回配置）叫 `CaptureFrom`，只有 scatter / cubewire / meshbg / space 四个配置实现了，
  且按设计只给编辑器"拾取"用，运行时不接。

### 27.4 `MarkDirty()` 为什么是 abstract，而不是基类给个空实现

空实现的 `MarkDirty()` 通过基类引用调用时**静默什么都不做**——参数改了、值也进去了、画面不动、报表也看不出错
（"零要说出它零在哪一层"那一族）。抽象把这件事交给编译器：**9 个工具必须各自说清"我的脏位是哪个字段"**。
同族还有一种只出警告的错法：派生类写 `public void MarkDirty()`（少一个 `override`）＝ CS0108 隐藏，
编译过、基类调用失效——`dirty_gate.py` 专门有一支变异管这个。

### 27.5 判据（离线，源码门）与它到底判了什么

工具要建 GameObject，engine 的 mono 造不出它们，所以**运行时探针够不着 setter**——能离线判的是声明清单的形状，
而形状恰恰就是这句主张的形状（"设了属性，渲染器就更新"）。`.ximage-gate/dirty_gate.py`：

- 清单**两侧都数**：`TOOLS` 里点名的 9 个文件 vs 磁盘上 `Runtime/XChart/**/ChartTool*.cs`，多一个少一个都红（M5）。
- 每个**外部可写**属性必须落在一条生效路径上：`MarkDirty(`，或本文件里定义了名字的 `Sync*/Push*/Apply*/Rebuild*(`。
  读数：`knobs=132 takesEffect=132`——122 支走 `MarkDirty`，**10 支走 `SyncShapeParams`（这 10 支是门查出来的，
  不是我原本知道的：散点外观那 10 个早就自带生效路径，于是判据从"必须调 MarkDirty"改成"必须调到本文件定义的生效方法"）**。
- 另外两条同门判据：
  **D** 工具不许在 setter 之外给自己的旋钮赋值（那会在自己渲染的过程中把自己重新置脏 ⇒ 每帧重建）；
  **E** 靠 `Sync` 生效的，`OnInitialize` 里也必须有那一句——否则 `if (IsInitialized) Sync()` 把初始化之前的写全丢掉。
- `{ get; private set; }` 归 **views**（只读投影，不是旋钮）。这一条不分类的话第一轮报出 26 处"自赋值"，
  全是 `FillRenderer = CreateChildComponent…` 这种初始化写盘——**分类之后真违规 0 处**（写了判据才知道有没有）。
- 七支变异各红在自己点名的那条：M1 抹掉一个 setter 的 `MarkDirty()`、M2 拿掉 `override`、M3 新增一个裸自动属性、
  M4 工具自赋值、M5 把一个工具从路径上挪走、M6 `SyncShapeParams()` 写成不存在的名字、M7 从 `OnInitialize` 删掉那句 `Sync`。

本轮自己的两处错，都是被门/编译门抓住的（不是现场）：批量改写脚本**把字段行的等号漏了**
（`private float m_Radius 0.22f;`，121 处全中——形状判据"这种形状的行了 0"＋编译门各报一次）；
判据把标识符里的字母当关键字（`Offset` 含 "set" ⇒ 只读的 `Offset` 被读成"有个从不置脏的 setter"），改词边界 `\bset\b`。
编译门：runtime + player + editor + 3 支对照 `GATE PASSED`（`chain_p20b.txt rc=0`）。

### 27.6 覆盖不到什么 / 还没做的

- **配置那一层还没有公开写入口**：`Element<T>()` 拿到的实例，字段仍是 `private`（面板走 `SerializedProperty`，
  本来不需要公开属性）。要"从代码写配置、并且活得过重建"，下一步给配置开属性 + 写完自动 push——
  否则那又是一条"改了没反应"。

## 28. P21：矢量场没渲染——根因是"数据值被当成立方体单位"（2026-10-26）

### 28.1 现场与读数（读数取自他自己的资产，不是猜的）

他报"矢量场现在没有在渲染"。我从 `Assets/Prefabs/0n_Panel/SP_盾构机掘进姿态 Variant.prefab` 里直接读到：

⇒ 形状是够的（需要 3、现有 3；面板那句"一条都不画"不会亮，报表 `dims=3/3` 也正常），
所以问题不在 §25.1 那一层，而在**尺度**这一层。

### 28.2 根因：同一件事两套口径，漏的那个不报错

`ChartToolVectorArrows.ReadPoint` 把 `GetValueAt` 的**原始值直接当立方体单位**用（±1＝盒子边界），
于是 −100..50 这份表把每支箭头投到**一万多像素之外**：支数在算、面在提交、计数全对，画面上什么都没有。

散点和圆柱一直是"按各维显示范围折进盒子"的（`context.TryResolveDomain` + `XChartBindingMath.TryNormalize`）
⇒ **只有箭头这一条路径没折**。这就是本规范反复在拆的那一族的又一种形状：同一件事两套口径，
坏的那一套不抛、不报错，只是看不见（§22 的格线双作者、§24.5 的序号双口径，同族）。

也不是 P20 改坏的：那次提交 33 增 17 删**全在属性形状上**，编译门绿，
他的 `Editor.log` 里这次导入只有一条无关的 `CS0414`——排除归因用的是"diff 里除形状之外没有别的行"这一条。

### 28.3 落法：折法进纯算术，范围每帧现问，读数印在报表里

- 新增 `XChartVectorFieldMath.TryCubePoint(x, y, z, minX..maxZ, out cube)`：每一维按**它自己的显示范围**
  映到 `[-1,1]`。**任何一维折不出来（跨度 ≤0、值或端点非有限）就整体拒答**——半归一化的坐标比不
  归一化的更难查：它会画出一个"看着像个箭头、方向却不对"的东西。折法放进纯算术是为了离线钉得住。
- 工具侧：三条轴的范围**每帧现问上下文**（覆盖优先，否则该维聚合；范围不归元素存，与散点同一条规矩），
  读点改成 `TryReadPoint`，读不出来的点计入 `skipped=` 而不是静默少画。
- 报表新增两个读数：`dom=x[..] y[..] z[..]` 与 `skipped=`。**折不出来就印 `dom=-`，那时一支都不画**
  ——"为什么没有"当场说话，不用回去猜。（他这份表应当印出 `dom=x[-100..50] …`、`arrows=记录数−1`。）

### 28.4 判据

   现在箭头这条路上没有"填充"那一层了，读数能给的解释比上一版窄——这正是这次改动的目的。

## 30. P24：方向来源四档、头的尺寸吃投影、锚点字段（2026-10-26 他三条要求）

### 30.1 他指出的两件事

1. **"矢量被归一化到屏幕空间再算了"**：圆周方向的一圈矢量，投到 2D 上不可能一样长，而他看到的一样长。
   成因在库那一行——`CurveMeshGenerator.cs:150  pos += tangent * arrow.width * 0.5f * arrow.depthCompensation`：
   标记的**方向**跟着曲线切线走（对），**尺寸是固定像素**（≠投影结果）。杆是两端点投影画的，所以会缩短；
   头不缩 ⇒ 整支读起来就是"屏幕空间里等长的箭头"。
2. **`Absolute` 下"方向的来源"应该是可选的**，而且支数要跟着一起来：
   他说"要让一个箭头对应两组数据，32 个点上就只该有 16 个箭头，而现在有 32 个"。

### 30.2 四档方向来源（`XChartArrowDirectionSource`，算式全在 `XChartVectorFieldMath`）

| 档 | 起点 | 方向／第二量 | 支数 | 要几个数值维 |
| --- | --- | --- | --- | --- |
| `NextRecordAsVector`（旧 Absolute） | 第 i 条 0~2 | 第 i+1 条 0~2（折进盒子后的坐标当方向） | N−1 | 3 |
| `NextRecordAsPoint`（旧 Relative） | 第 i 条 0~2 | 第 i+1 条 0~2（**第二个点**，作差） | N−1 | 3 |
| `ThisRecordCarriesVector` | 第 i 条 0~2 | **同一条**的 3~5（原始矢量） | N | 6 |
| `AlternatingRecords`（分段） | **偶数**条 0~2 | **奇数**条 0~2（原始矢量） | N÷2 | 3 |

- **支数与维数只有这一个实现**：`ArrowCount(source,…)` / `RequiredCoordinateDimensions(source)`。
  四档的算法（`N−1 / N / N÷2`、`3 / 6`）一旦在工具里各写一遍，画面上只是"少几支"，最难查。
- **方向是原始矢量，绝不按位置的显示范围折**（`TryReadRaw`）：折一次就把"朝哪"变成"在哪"——
  一个 `(0,1,0)` 会被折成一个偏移量，于是整场箭头一起跑偏。它的尺度由 `DirectionScale`（每数据单位给多少立方体单位）说话。
- **兼容**：新枚举的 0/1 就是旧 `XChartArrowVectorMode` 的 Absolute/Relative，字段另加了
  `[FormerlySerializedAs("m_VectorMode")]` ⇒ 他场景里存过的值不用重设（"换类型不换序号"是"改名静默丢值"的反面做法）。
- 他说"相对模式是一个点到另一个点，不用再算一次投影"：这条本来就成立（两端都是投影点），
  所以 `Tip` 只在 `NextRecordAsPoint` 那一档作差，其余三档第二量直接就是方向。

### 30.3 头的尺寸吃投影 + 锚点

- `ProjectedScale(投影像素, 立方体长度, CubeToPixel)`＝这条矢量的**投影比例**：平行于屏幕＝1、指向屏幕里→0；
  头的两个尺寸都乘它（连续绘制那一档取**这一节自己**的比例，所以弯到背面去的那一节头也跟着缩）。
  除不出来（NaN、零长、零比例）就答 **0**：宁可头缩成没有，也不要一个凭空的固定尺寸。
- `MarkerAnchor` [0,1] → 库的 `depthCompensation`（`anchor×2−1`）：**0＝尾部落在点上（向前伸）、0.5＝中心、1＝头尖落在点上**（默认 1）。
  非有限数退回 1——"头该贴在哪"不该因为一次写坏的值变成位置未知。
- `XMeshPreviewChart` 那份"一条记录 6 维、方向存 3~5 维"的旧示例数据，在 `ThisRecordCarriesVector` 这一档下
  **正好是合法的**（§28.5 里我说的"死数据"从此有了读法）——我没有替他把默认值改掉。

## 31. P28：面边插槽 6×4＝24（"贴哪一面的哪条棱"终于说得出来，2026-10-26）

### 31.1 他数出来的两件事，和它们各自的真相

- **"下拉里有 12 个，只有 mesh.face.1-5 有用，后面的 grid.S/T 都没用"**：完全对得上字面——板上现在只有两类 id：
  `mesh.face.<0..5>`（Quad3D，面四角，6 个）与 `mesh.face.<n>.grid.S|T`（**Line3D 比例数组**，12 个）。
  而轴线只认 `Quad3D`（`ChartToolAxis.ResolveFaceFrame`），所以那 12 条在这个下拉里**永远是死项**——
  它们是「对齐格线」那一栏的输入，不是宿主。
- **"4 条垂直边注册不上"**：不是漏发布，是**"边"根本不是一个可寻址的东西**。以前要贴一条棱只能"选一个面 + `CrossRatio=±1`"，
  而一根立方体棱被两个面共享，两面的面内方向又不同 ⇒ 同一根棱有两种参数化，其中一种落不到你要的位置。

### 31.2 落法：一条边＝一个"旋到底边的面帧"，仍是 Quad3D

- id：**`mesh.face.<f>.side.<s>`**，6×4＝24 个。前缀沿用 `mesh.face.`（`TryGetSlotAt`、轴从 id 回落读面号都按它解析；
  换成 `mesh.face0.side0` 那种写法就会同时存在两套前缀）。
- **值**＝同一个面的四角、按 `<00,01,11,10>` 这个环旋转 `s` 格，让**选中的那条棱正好落在面帧的底边（S 轴、t=0）**。
  于是它还是一个 `Quad3D`，轴线的 `AlongS`／`CrossRatio`／刻度朝外／标签随轴旋转**一行都不用改**；
  绕序保持不变 ⇒ 不会镜像（镜像了"往面内刻度"就会翻到外面去）。
- 边号：`0 底 · 1 左 · 2 顶 · 3 右`（环上逆时针），名字由 `SideName` 给，面板与报表同一个来源。
- **发布者只有一个**：线框元素（它就是画棱的那个，`mesh.face.<n>` 也是它发的）——一处算式出 24 份，

- 面板下拉**只列能当宿主的**，并明说"另有 N 个比例数组插槽是给对齐格线用的"。
  判据只有一处：`ChartToolAxis.CanHostAxis(mode)`——消费者与面板共用它，否则会出现"下拉里能选、线上画不出"。
  轴那行的 `slot=` / `frame=slot|cube` 早就有了，所以"我到底贴上了哪条边"当场可读，不必再加新读数。

## 32. P27：显示范围只定标尺；数据图元自己决定"钳 / 藏 / 原样"（2026-10-26 他裁定）

### 32.1 症状：同一张表两幅画

散点折进盒子时用的是 `Mathf.Clamp01`（`ChartToolScatterPoints`），所以超范围的点**钉在盒壁上**——看着像"数据到边就停"；
而矢量与圆柱按 `TryNormalize` 比例投，**可以跑到盒子外面**。两边都"看着挺对"，谁也没报错。
（再往前，箭头连折都没折，那就是 §28 的"计数全对、画面空无一物"。）

### 32.2 口径：范围的本分是定标尺，不是决定数据画不画

- **轴线与格线永远用它**——不给开关。否则会出现"格线按 A 范围铺、刻度按 B 范围标"，那正是 §20 一路在拆的东西。
- **数据图元**（散点、矢量箭头、圆柱；以后的标签同理）各有一个三档开关 `XChartValueOutOfRange`，**默认 `RenderAsIs`**：
  `RenderAsIs` 按数据自己的值投（可以出盒外，"呈现自己准确的位置"）· `ClampToRange` 夹到范围端点 · `HideOutOfRange` 整条不画。
- 隐藏是**整条记录**，不藏一半坐标：只夹一轴会画出一个"数据里不存在"的位置，比少画一条糟得多。

### 32.3 一份折法，三处调用

新纯算术 `XChartCubeFoldMath`：`TryRatio01(value, min, max, behaviour, out 0..1)` 是**唯一**的"值 → 盒子内比例"，
`TryFoldCube` 是它的三轴全有或全无版（[-1,1]）。圆柱原来调 `XChartBindingMath.TryNormalize`、
箭头调 `XChartVectorFieldMath.TryCubePoint`、散点调自己那份 `Normalize`——**三份并成一份**，箭头的 `TryCubePoint` 删除。

删除那一步被门抓了一次，而且抓得对：`dirty_gate` 的 claim F 当场报 FAIL（"箭头的坐标不再经过折法"）。
它判的是**"坐标必须经过唯一那份折法"**，不是"必须调用某个旧名字"——所以搬家的正确处置是把门指向新来源，
**删判据是错的处理**。九支变异里 M8 这一轮顺手证明了这件事：把旧形状（原始值直接进 `Vector3`）塞回去，门红。

还有一处刻意**不统一**：颜色映射那一档继续夹（`Normalize` 只服务它）。越界的颜色取端色是常态，
"隐藏超出范围的数据"是坐标的事——把梯度也弄出洞来才是灾难。这条写进注释，防止下次有人"顺手统一"。

### 32.4 这次改到的两处默认行为（他要看得见的）

1. **散点不再贴边**：默认下超范围的点画在盒子外面（UGUI 不裁，所以会画到图外）。想让点限定在网格内就把这一档调成 `ClampToRange`。
2. **一整列同一个数**以前让矢量整条拒答（跨度 ≤0 ⇒ `false` ⇒ 少画），现在答**居中**；
   坏数（NaN/Inf）仍旧拒答。理由：为"我还没钉范围"把整个元素弄没，等于把状态误报成"这里没有数据"（§25.1 同一条精神）。

读数跟着补了两个：`out=asis|clamptorange|hideoutofrange`（这一档选的是什么）、
`hidden=`（按策略隐掉的条数）与 `skipped=`（数据不可用的条数）——**"我主动不画"与"数据不能用"必须分得开**。
